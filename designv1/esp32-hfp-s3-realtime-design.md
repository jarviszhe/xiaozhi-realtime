# ESP32 HFP 电话网关与 ESP32-S3 Realtime AI 双芯片设计

日期：2026-11-18

状态（更新于 2026-11-27）：两端已恢复无线 UDP 并烧录，经典 ESP32 在 SCO 通话期间保持 Wi-Fi 开启。Android 实机独立上下行语音、原始/接收录音 ASR、候选断音和 UDP 统计已完成本轮量化，详见第 18.28 节；首轮上行越窗/字符差异、蓝牙坏帧及下行弱声学拾音仍未通过。UART 保留为未来实验方向。完整双讲、真实来电生命周期和当前镜像长稳尚未验收，历史单项结果不提升为整体通过。本文带宽是计算值，未实测的时延与兼容性指标仍为目标。

## 1. 目标与架构

用初代 ESP32 连接手机的蓝牙通话音频，用 ESP32-S3 承担阿里云 Realtime 会话。远端来电人的声音进入 AI，AI 回复通过手机发送给远端，实现电话中的 AI 对话。

```text
远端通话人 ↔ 运营商电话 / 手机 VoIP 应用
                          ↕
                    手机（HFP AG）
                          ↕ Bluetooth Classic HFP / SCO 或 eSCO
                 初代 ESP32（HFP HF）
                          ↕ 局域网 UDP，双向 PCM / ADPCM / Opus
                 ESP32-S3（Realtime 主机）
                          ↕ TLS / WebSocket，按模型要求传 PCM
                    阿里云 Realtime
```

“电话网关”是本系统的用途名称。蓝牙协议角色应为 **ESP32 = HF / Hands-Free Client，手机 = AG / Audio Gateway**，不能因为名称叫网关而选用 `hfp_ag` 示例。[S1]

初代 ESP32 提供本方案所需的经典蓝牙 HFP；ESP32-S3 只有 Bluetooth LE，不能直接替代经典蓝牙 HFP 端点。两颗芯片的分工以此为基础，不能把 BLE 或 A2DP 当成双向电话音频的直接替代。[S1][S2]

首版只连接一部手机、处理一路通话。2026-11-18 增加普通电话来电指示后延迟 3 秒自动接听；复杂通话保持、多手机切换和全双工插话放到后续独立评估。

开发阶段先以 Windows 电脑代替手机充当 HFP AG，通过固定 WAV 播放与录音验证双向音频，再逐步加入 UDP、S3 和云端。真实手机通话与微信兼容性在后期单独验收，日常音频调试不要求反复拨打电话。

## 2. 两端职责与工程边界

## 3. HFP 音频获取与数据流

### 3.1 HFP 数据路径

优先选择 HCI/vHCI 音频路径，在应用层桥接音频；不把控制器 PCM 引脚路径误认为已自动进入 UDP。官方示例区分这两种路径，并提供 CVSD 与 mSBC 的配置说明。[S1]

首版在内部统一为单声道 PCM16，再做局域网编码。CVSD 通话按 8 kHz PCM、mSBC 宽带通话按 16 kHz PCM处理；实际启用的编码必须由协商事件与数据路径验证，不以“支持宽带”或手机支持 VoLTE 推断已经使用 mSBC。[S1]

特别注意 IDF 6.1 官方示例存在内部编解码的旧式 PCM 回调路径，以及 `CONFIG_BT_HFP_USE_EXTERNAL_CODEC` 下的新音频缓冲回调路径。后者可能交付 mSBC 编码载荷，不能把所有 HCI 回调内容都解释为 PCM16。阶段一须确认选用路径、帧格式、缓冲所有权和释放时机；选外部编解码时必须补全对应解码/编码。[S3]

蓝牙回调只执行有界复制或缓冲所有权转移和队列通知；UDP、Opus、重采样及日志写盘在工作任务运行。发送失败和队列满要有明确回收与丢帧计数，不能阻塞蓝牙栈。

### 3.2 手机声音进入 AI

1. 手机将远端通话声音经 SCO/eSCO 发送到 ESP32。
2. ESP32 获得或解码为 HFP 原生采样率 PCM，按 20 ms 组帧。
3. ESP32 编码局域网载荷，携带序号、样本时间戳和会话代次发送 UDP。
4. S3 通过抖动缓存恢复时间顺序，解码并转换到云端输入采样率。
5. S3 将 PCM 按现有 Realtime 协议上传，由手动提交或云端 VAD 完成分轮。

### 3.3 AI 回复进入电话

1. S3 收到云端回复 PCM，根据实际模型会话确定采样率。
2. S3 重采样到 HFP 协商采样率，按局域网格式编码发送。
3. ESP32 经抖动缓存和解码后，按蓝牙发送节拍填充 HF 麦克风方向音频。
4. 手机把这一路作为蓝牙麦克风输入发送给远端通话人。

局域网 Opus 与 HFP mSBC/CVSD 是独立编码层；首版不直接透传 mSBC 到云端。Opus 解码后才转换为云端要求的 PCM，不假定阿里接口接受任意 Opus 裸包。

云端先沿用现有集成的格式，目标基线为输入 16 kHz、输出 24 kHz、单声道 PCM16。阿里官方不同模型/SDK的采样率配置能力有差异，实施时固定模型和配置，不能将该基线写成所有 Realtime 模型的统一限制。[S4]

## 4. PCM、ADPCM、Opus 带宽比较

以下均为单声道、单方向，`kbit/s = 1000 bit/s`。以 20 ms 一包计算，每方向 50 包/秒；IPv4+UDP 为 28 字节，再假设自定义头 32 字节，则每方向固定增加 24 kbit/s。未计 Wi-Fi MAC/PHY、加密、ACK、竞争退避及重传。

| 局域网格式 | 采样率 | 音频有效载荷 | 每包音频字节 | 加上述头部后单向 / 双向 |
| --- | --- | --- | --- | --- |
| PCM16 | 8 kHz | 128 kbit/s | 320 | 152 / 304 kbit/s |
| PCM16 | 16 kHz | 256 kbit/s | 640 | 280 / 560 kbit/s |
| PCM16 | 24 kHz | 384 kbit/s | 960 | 408 / 816 kbit/s |
| 4 bit IMA ADPCM，理想载荷估算 | 8 kHz | 32 kbit/s | 80 | 56 / 112 kbit/s，另加块状态 |
| 4 bit IMA ADPCM，理想载荷估算 | 16 kHz | 64 kbit/s | 160 | 88 / 176 kbit/s，另加块状态 |
| Opus，拟定固定目标码率 | 8 / 16 kHz 输入 | 16 kbit/s | 约 40 | 约 40 / 80 kbit/s |
| Opus，拟定固定目标码率 | 8 / 16 kHz 输入 | 24 kbit/s | 约 60 | 约 48 / 96 kbit/s |

计算公式：PCM 码率 = 采样率 × 16；ADPCM 理想码率 = 采样率 × 4；包开销 = 60 × 8 × 50。ADPCM 的预测器和步长索引等块状态会增加实际码率；Opus 若使用 VBR、FEC 或改变帧长，实际包长也会改变。上表不是实测网络吞吐或射频占用。

建议先用 PCM 建立正确性基线，再测试逐包独立状态的 IMA ADPCM，最后以 **16 kHz 单声道、20 ms、16–24 kbit/s Opus** 作为候选正式格式。Opus 支持交互语音和 20 ms 帧，但初代 ESP32 上的编解码 CPU、内存与时延必须实测后决定。[S5]

Opus 可降低传输字节，不能承诺同比降低 Wi-Fi 空口时间；小包下固定开销占比显著。ADPCM 的每包应独立携带恢复状态，避免一次丢包污染后续整段音频。禁止用“ADPCM”名称代替明确的编码格式、块布局和互通测试。

## 5. UDP 与 Bluetooth 共存

UDP 是传输协议，实际链路仍使用 ESP32 的 2.4 GHz Wi-Fi。初代 ESP32 的 Wi-Fi 与 Bluetooth 共用射频并采用时分仲裁，因此“改成 UDP”不能消除与 SCO/eSCO 的竞争。[S6]

首版拓扑建议两颗芯片都以 STA 接入同一个外部 AP。初代 ESP32 通话时避免扫描、配网、OTA和大流量诊断；启用软件共存，按官方建议评估 Wi-Fi 与蓝牙任务分核运行。不要未经测试就修改底层共存优先级。[S6]

外部 AP 转发意味着一次芯片间单向传输通常经过 STA→AP、AP→STA 两段无线发送；带宽表仅计算 IP 流量，不能直接当成空口预算。S3 还需访问云端，测试须把其真实云流量一并纳入。

S3 SoftAP + ESP32 STA 可作为独立对照拓扑，但 S3 的 STA 上网与 SoftAP 信道约束、转发路径、断网行为必须单独验证，不把它当成天然更稳定的方案。两颗芯片使用独立射频也仍可能互相干扰，天线距离和供电需实测。

先分别测 HFP 单独运行、HFP+空闲 Wi-Fi、HFP+双向 PCM、HFP+ADPCM、HFP+Opus，再加入云端流量和弱信号。记录坏 SCO 帧、丢包、迟到包、欠载、CPU 与内部堆余量，区分射频损伤与任务处理不及时。

若压缩、限流和调度优化后仍不能达标，保留有线 SPI/UART/数字音频桥接为备选。它是后续决策分支，不能在未评估接线、时钟、电平及新板身份前直接实施。

## 6. UDP 包、控制与会话隔离

以下为拟定协议字段，阶段二需明确字节偏移、网络字节序和版本兼容规则，再编码实现：

| 类别 | 必需信息 |
| --- | --- |
| 包识别 | magic、版本、头长、载荷长、音频/控制类型 |
| 会话隔离 | 启动标识、通话代次、媒体方向；取消时额外递增回复代次 |
| 音频解释 | codec、采样率、单声道标志、每帧样本数、编码附加状态 |
| 排序与播放 | 每方向独立序号、源样本累计时间戳、流重置/静音标志 |

32 字节只是带宽计算的占位预算；字段落定后重新计算。不要原样发送带填充的 C struct。限制 UDP 数据报总长不超过 1200 字节，超过即拒绝或重新设计帧长，不依赖 IP 分片。

媒体不重传过期音频，丢帧后做 PLC 或短静音并计数。控制消息使用命令 ID、确认、超时和有界重试，接听、挂断、重置应幂等；同一条接听命令重试不能变成第二次操作。

建立会话握手后才接受媒体，验证来源、长度、codec、采样率、帧样本数和代次；重启、断线、挂断、取消回复时清空对应队列和解码状态。生产版本须定义配对认证和防重放机制；单靠来源 IP 只适合受控原型，不算身份认证。

## 7. 重采样、节拍与抖动缓存

HFP 原生 PCM 与局域网传输优先保持同一采样率，重采样集中在 S3 的云端边界：电话 8/16 kHz → 云端输入 16 kHz；云端输出 24 kHz → 电话 8/16 kHz。若模型使用其他格式，以实际协商配置为准。

降采样必须使用抗混叠滤波；升采样不会恢复窄带电话已丢失的频谱。采用流式、有状态的重采样器，帧间保留滤波状态，不逐包重置。

每方向独立设置抖动缓存，初始目标 40–60 ms，可在 20–100 ms 范围内调整；超过最大音频年龄的包丢弃，不能为追求零丢包而无限增加延迟。序号处理乱序和重复，样本时间戳驱动播放节拍。

两颗芯片和蓝牙时钟可能有长期频偏。持续监控缓存水位和累计样本差，用缓慢自适应重采样或有平滑处理的样本修正消除漂移；禁止每隔数秒粗暴丢掉一整帧而不记录。

单个 16 kHz PCM16、100 ms 缓存约 3.2 KB，两方向约 6.4 KB；这仅是解码后音频，不包含 Opus 状态、蓝牙/Wi-Fi 栈、队列和任务栈。初代 ESP32 内部堆最小余量与最大可用块必须在完整负载下测量。

## 8. 电话轮次、取消与故障恢复

首版沿用现有 [Manual / Auto 设计](aliyun-manual-auto-design.md) 的半双工原则：AI 回复期间不向云端上传远端讲话；回复结束且电话发送路径本地待发音频排空后恢复监听。播放期间仍及时消费 HFP 接收数据并丢弃，不积压到下一轮。

本地队列排空仅说明桥接端已送交蓝牙栈，不能证明远端已听完。恢复等待需结合 SCO、手机和通话链路测量。HTTP/串口日志的“发送完成”不能写成远端实际播放完成。

电话音频作为数字源时，首版不套用本地麦克风 NSNet/AFE/AEC。数字桥减少本地扬声器声学回授，但远端免提回声、手机或网络侧回声仍需验证。全双工插话、远端说话打断 AI 和回声抑制作为后续专题；本地唤醒词打断结论不能直接套到电话音频。

收到挂断、HFP 音频断开或链路超时后，停止该代上行、取消云端回复、清空两端媒体，拒绝旧代迟到数据。云端断线时停止向电话注入旧音频，并明确显示不可用状态，不在无确认的情况下循环自动拨号或接听。

S3 应用状态通过 `Application::Schedule()` 回到主任务，并由 `SetDeviceState()` 与状态机管理。电话链路状态与 AI 轮次分别记录，避免把“蓝牙已配对”当成“音频已接通”。

## 9. 普通电话与微信等 VoIP 的兼容边界

### 9.1 Windows 电脑优先调试

Windows 在 HFP 中可承担 AG，ESP32 仍承担 HF。Windows 支持 HFP 单声道同时播放与录音，因此日常测试可直接由电脑提供测试语音、接收返回音频，无须建立真实电话。[S8][S9]

```text
电脑播放固定 WAV → HFP → ESP32 → UDP → S3 → 阿里 Realtime
电脑录制返回 WAV ← HFP ← ESP32 ← UDP ← S3 ← 阿里 Realtime

电脑 USB → ESP32：供电、烧录、串口日志
```

| 电脑上的音频操作 | ESP32 侧方向 | 电话场景对应含义 |
| --- | --- | --- |
| 向 ESP32 对应的 HFP 播放端点写入 WAV | HFP 接收，随后向 S3 上行 | 远端通话人讲话 |
| 从 ESP32 对应的 HFP 录音端点读取 WAV | HFP 发送，承载 S3 下行 | AI 向远端通话人回复 |

USB 连接本身不作为本方案的 HFP 音频路径。2026-11-18 已在 Windows 10 / Intel 蓝牙上完成配对、HFP SLC、CVSD 与 mSBC 双向短测；详细验收与失败记录见第 11 节及独立网关实施记录。

Windows 10 可显式选择 Hands-Free 播放/录音端点；Windows 11 可能统一端点名称，打开该设备的麦克风输入可使系统选择 HFP。测试工具需保持输入与输出同时打开，显式记录端点 ID，不能只看“已连接”或播放设备名称认定在走 HFP。[S8]

HFP 音频连接不应依赖真实通话状态；固件须处理电脑 AG 在空闲状态发起的音频连接。[S9] 实施时以 ESP32 日志中的 SLC、SCO/eSCO、实际 codec 和收发计数为证，记录 Windows 版本、蓝牙适配器、驱动版本及所选端点。电脑 API 的音频格式可能经过系统重采样，不能用 WAV 的采样率反推 HFP 编码。[S8]

先确认 CVSD 路径可用，再验证 mSBC。若本机驱动或设备组合无法协商宽带，先记录为窄带通过、宽带未通过；不能把勾选宽带配置当成 mSBC 验收。若本机 HFP 无法建立，先排查服务声明、配对、驱动和音频连接状态；必要时以一部手机作对照定位，不能用 A2DP 或 USB 音频结果替代 HFP 验证。

电脑测试工具按以下顺序建设，放在新网关仓库的 `tools/` 下：

1. 枚举并选择蓝牙播放/录音端点，播放固定 WAV、录制返回 WAV，保存串口日志及测试元数据。
2. 在 ESP32 的 HFP 接收端保存短时有界 PCM 样本，发送方向独立注入测试音，先分别证明两条路径。环回仅作为明确开启的诊断模式，正常模式不把输入直接反馈输出。
3. 加入 S3 后，使用相同测试素材和参数验证 UDP 桥，再加入真实云端流量比较 PCM、ADPCM 和 Opus。
4. 接入 Realtime 后，固定问题集、重复次数、轮间等待和超时，自动保存每轮输入、回复、状态及失败原因，生成结果摘要。

首批测试素材包含静音、短测试音、中文短句和长句。先从较低音量确认无削波，并记录系统音量和音效设置；录制阶段避免把返回声音再次送入测试输入形成回授。音频环回成功不代表语音识别和对话正确，自动化结果仍需结合文本及录音抽查。

电脑验证覆盖 HFP 双向媒体、UDP、编码、共存、重采样、云端轮次和长稳测试；手机真实来电事件、AT 接听挂断、运营商链路、微信路由和远端回声仍必须通过手机验收。

### 9.2 手机与应用验收范围

| 场景 | 预期与边界 | 验证方法 |
| --- | --- | --- |
| 普通运营商来电/去电 | 以手机 HFP 通话路由为目标；协商编码和呼叫控制能力依手机而定 | 真实呼入呼出，双向声音、接听/挂断、路由切换 |
| VoLTE / VoWiFi | 不由运营商侧宽带能力推断 HFP 一定为 mSBC | 同时记录手机通话模式与实际 HFP 编码 |
| 微信语音通话 | 仅在该手机/系统/微信版本把双向通信音频路由到 HFP 时可用 | 应用内手动接听并选蓝牙，分别核对输入与输出 |
| 微信视频、其他 VoIP | 逐应用验证，不从微信语音结果推广 | 语音/视频分别测试，含锁屏和后台 |
| 微信语音消息、媒体播放 | 不纳入首版通话兼容承诺，可能使用不同音频路由 | 如有需求单独立项验证 |

Android 官方通信设备选择 API 说明语音/视频通话使用通信音频设备路由；这支持“VoIP 依应用和系统路由”这一判断，不能作为微信已经兼容的证据。[S7]

必须分别记录 **双向音频是否可用** 与 **HFP 按键/AT 接听挂断是否可用**。VoIP 可出现音频正常但 HFP 呼叫指示或远程接听无效的组合；首版允许在手机应用手动接听。

兼容结果需绑定手机型号、Android/iOS 版本、应用版本、ESP-IDF 提交、编码和固件版本。未测试项标为未验证；某一款手机通过不代表全部手机或全部微信版本通过。

电脑和手机的 codec 协商分别记录；若某设备不能协商 mSBC，仅能验收该设备的 CVSD 路径，宽带路径保留未验证，不能通过配置开启选项代替实测。电脑媒体测试与真实手机呼叫测试分开登记。P6 的 300 ms 从本地收到挂断事件算起，不包含手机事件到达前或远端已缓冲的声音。

时延测量优先使用同一时钟域或经校准的外部双通道录音/逻辑采集。不可直接用两颗芯片未同步的单调时间相减；无法校准时报告往返时延，不简单除二声称得到精确单向值。端到端体验测试须录到远端真实声音，云端 response.done 和 UDP 发送时间不足以代表听感。

每阶段保留样本数、分位数、测试时长、丢包与坏帧分母、队列峰值、堆最小值、复现步骤和固件哈希。采集点至少包含 HF 入站 PCM、云端上行 PCM、云端下行 PCM、HF 出站 PCM；这些仍不等于手机远端真实播放录音。调试抓取要限流、有界，单列其对共存性能的影响。

## 15. 2026-11-18 实际手机杂音后的修复与电脑声学验收

### 15.1 已定位问题与代码调整

- S3 的 8K/16K → 24K 线性插值曾混用有符号差值和无符号插值权重，使下降沿发生整数回绕；现统一使用有符号计算，并在启动时检查两种输入率的正负满幅交替样本。
- FreeRTOS 为 100 Hz 时 `pdMS_TO_TICKS(2)` 等于零，桥接空转曾触发 `IDLE1` 看门狗；现每轮至少等待一个 tick，包括重复包和无效包分支。
- 连续 PCM 播放曾在队列暂空时等待整个 60 ms DMA 尾部；PCM 桥接模式不再采用该有限音频播放等待。
- 桥接开始和新媒体会话时通过 Board 接口切到 Wi-Fi PERFORMANCE，避免启动完成后的省电状态继续影响通话。
- S3 起播先缓存 4 个 20 ms 帧，即 80 ms；会话变化或接收间断超过 200 ms 时重新起缓冲。这是有限起播缓存，尚不是完整的乱序、丢包补偿和时钟漂移校正器。
- S3 日志增加 `seq / gaps / reordered / queue_drops / max_gap_ms`；其中 gaps 为按到达顺序观察到的序号缺口，不能当成经过等待和重排确认后的最终网络丢包率。
- 网关只对经过 H2/mSBC 同步检查的帧调用正常解码，移除猜偏移直接送解码器的兜底；补偿帧正确标记为 concealed。
- 网关增加外部编解码配置的编译检查，避免内置 HFP 编解码与应用层 SBC 实现同时启用。

## 17. 2026-11-23 S3 主导的自动配网、发现与绑定方案（已实施调试版）

本节记录讨论确定的设计和当前固件实现范围。当前调试版已经支持：S3 串口发现、BLE 加密配网、经典 ESP32 实体按键授权、Wi-Fi 配置持久化、局域网控制握手和 UDP 音频模式恢复。完全空白的芯片仍需先烧录固件。经典 ESP32 无屏幕，S3 有屏幕；当前调试阶段不增加屏幕入口，使用 S3 串口命令，后续屏幕复用相同业务接口。

### 17.1 职责和通道

- S3 是配置管理端：获取自身当前网络凭据、扫描网关、发起配网、保存绑定、发现和重连网关、查询状态。
- 经典 ESP32 是被配置端：广播配网入口、处理实体按键授权、保存网络和绑定、反馈联网结果、承担手机 HFP 电话音频。
- BLE 用于首次配网及换网恢复；Wi-Fi 用于联网后的控制连接和 UDP 双向音频。原 Wi-Fi 不可用时，仍能通过 BLE 更新配置。
- 两板音频桥就绪与手机 HFP 连接、SCO 通话音频建立分别报告。两板自动配网不会代替手机首次蓝牙配对，也不会自动拨号。

### 17.2 设备身份、按键确认与绑定

设备 ID 由经典 ESP32 的出厂 MAC 派生，使用完整地址对应的标识，例如 `GW-A1B2C3D4E5F6`；显示名称可缩写，绑定时不得只使用短后缀、显示名称或 IP。设备 ID 稳定但公开，不是认证密钥。

本方案取消手工输入配对码，改为设备实体按键授权。经典 ESP32 无配置时可以广播待配网状态，但接收广播或建立 BLE 连接不等于授权写入配置。S3 发起请求后，网关只保留一个有明确超时的待确认会话；用户短按按键，仅授权该会话。请求取消、连接断开、超时均撤销待确认状态，确认不能沿用到下一次连接。多个请求不能覆盖已展示的待确认请求。

长按约 3 秒清除经典 ESP32 保存的 Wi-Fi 配网信息（SSID、密码和候选网络配置），停止旧网络重连，并进入限时重新配网窗口，窗口建议 120 秒；保留 S3 绑定和手机蓝牙配对记录。窗口内短按完成当前请求确认；更换绑定仍需独立的会话授权，清除 Wi-Fi 不自动解除绑定。长按每次按住只执行一次，松开不能再次被解释为确认短按。清除操作需检查持久化结果，通过串口报告成功或错误，不能在清除失败时报告已恢复未配网状态；重启后也不得重新加载已清除的旧网络。具体 GPIO、去抖和启动按键限制应先核对实板，不能直接假定任意 BOOT 按键均可安全复用。

配网会话仍需加密，按键只表示物理授权，不等同于配对码提供的身份认证。BLE 安全握手、会话绑定及抗抢占边界须在实施前明确；不得把未认证的加密宣称为完整身份认证。首次授权后建立独立随机绑定凭据，用于后续双向身份校验；Wi-Fi 密码和绑定密钥不出现在广播、状态输出及普通日志中。

#### 17.2.1 原理图核对后的按键选择

经典 ESP32 原理图 `docs/datasheet/ESP32-DEV-KIT-XX.pdf` 中，Key1（BOOT）连接 GPIO0，按下接地，R10 为 10 kΩ 上拉到 3.3 V，可用作低电平有效的业务按键；Key2（RESET）连接 EN，按下会复位芯片，不用于配网确认或长按计时。计划在固件正常运行后复用 Key1：短按确认当前配网会话，长按约 3 秒清除 Wi-Fi 配置并进入重新配网窗口。上电/复位、串口自动下载对 GPIO0 的影响须在实现及实板测试时覆盖；程序启动时已经按住的按键需先释放，不能直接计为清除配置。

S3 不增加任何实体按键操作：当前使用串口扫描、配置和查询状态，后续使用屏幕入口；不占用或修改 S3 现有 BOOT 按键行为。

#### 17.2.2 经典 ESP32 RGB 状态指示（设计保留，尚未纳入本轮验收）

依据 `docs/datasheet/ESP32-DEV-KIT-XX.pdf`，板载 LED1 为 WS2812B-0807，DIN 经 R1（0 Ω）连接 GPIO27（RGB_CTRL）。使用该可编程 RGB 灯指示网关状态；电源及充电指示灯不作为软件状态灯。WS2812B 通过单数据线时序接收颜色数据，由灯内控制芯片驱动各颜色通道，不使用普通 GPIO 高低电平或三路 PWM 直接选择颜色。实现时使用适配 SDK 的驱动，并以实板核对颜色通道顺序和显示效果。

| 灯效 | 含义与触发条件 |
| --- | --- |
| 蓝灯慢闪 | 配网窗口已开启，等待 S3 发起请求；窗口结束则熄灭，不继续表示可以配网 |
| 蓝灯快闪 | 已有唯一待确认配网/换绑会话，等待用户短按 Key1；超时或断开后退出 |
| 黄灯慢闪 | 已配置，正在连接 Wi-Fi、发现 S3 或完成控制握手；具体阶段由串口区分 |
| 绿灯常亮 | 已通过绑定身份校验，控制握手完成，音频桥就绪；不表示手机已连接 |
| 绿灯慢闪 | 音频桥就绪且手机 HFP/SCO 通话音频已建立；断开或媒体失效立即退出 |
| 红灯闪烁 | 配网失败、身份校验失败或链路异常，串口保留具体错误和发生时间 |
| 蓝灯短亮一次后慢闪 | 用户长按清除 Wi-Fi 配置且持久化成功，随后进入等待重新配网；清除失败用红灯和错误日志反馈 |
| 熄灭 | 状态灯尚未初始化，或无网络配置且配网窗口已关闭；不代表设备一定断电 |

建议慢闪周期约 2 秒，快闪周期约 0.5 秒，清除成功提示约 0.5 秒，实际节奏以实板易辨识为准。RGB 保持低亮度，初始单色通道值约 15/255，黄色同时使用低亮度红、绿通道，避免全亮。灯效由独立、非阻塞的定时状态更新驱动，不在 HFP 回调或音频任务中等待灯效、反复分配缓冲或频繁刷新。

所有业务事件先归一为单一显示状态，不允许多个任务直接抢写 RGB。配网失败/异常提示和清除成功反馈应有明确显示时限；后续用户重试、新连接或恢复成功清除旧提示，回到当前真实状态。基础状态优先级为：当前有效错误提示 > 等待按键确认 > 配网等待 > 网络/握手恢复 > 通话音频建立 > 音频桥就绪 > 熄灭；清除成功的一次性反馈在切换到配网等待前显示。错误提示期间仍允许用户重新发起恢复操作，不应永久覆盖后续阶段。通话期间若链路失效，应显示恢复或错误状态，不能因 SCO 尚未断开而继续显示绿色通话灯。

绿色只说明连接状态满足条件，不证明麦克风、扬声器、双向可懂语音或无卡顿。`gateway status` 应同时返回当前灯效状态及触发原因，便于核对状态显示和实际链路是否一致。后续验收补充各状态灯效、超时退出、错误恢复、长按单次反馈，以及通话期间灯效更新不影响音频连续性。

### 17.3 首次配网流程

1. 网关检测到未配置，进入 BLE 待配网广播；S3 已连接路由器。
2. 在 S3 串口执行 `gateway scan`，取得设备 ID、信号强度和是否已绑定等信息。扫描结果中的绑定声明在验证前只作为提示。
3. 执行 `gateway provision <设备ID>`。S3 建立配网会话并提示“请短按网关按键确认”；网关等待本次会话的物理确认。
4. 用户短按网关按键，S3 通过加密会话发送当前 Wi-Fi 名称、密码、S3 身份及绑定所需信息。日志仅记录阶段与结果，不记录凭据。
5. 网关尝试联网，经 BLE 返回成功及当前 IP，或密码错误、找不到 AP、DHCP 超时等失败原因；失败允许重试，不得把“配置已发送”当作联网成功。
6. 网关联网后发布发现服务；S3 发现地址、验证绑定并协商音频参数，双方确认就绪后启用音频桥。
7. 配网结束关闭配网广播和扫描。网关保留 HFP 所需蓝牙资源，不能在退出配网时释放经典蓝牙或整个蓝牙控制器资源。

配置和绑定采用候选状态及确认状态，检查 NVS 写入结果，约定中断后的重试与恢复；不能因为某一端保存成功就把整个绑定标为完成。上电检测到未完成事务时应允许已授权会话恢复或重新确认，不静默进入错误绑定状态。

### 17.4 后续上电与局域网握手

两端自动读取保存的网络和绑定配置，各自连接路由器。经典 ESP32 发布 mDNS 网关服务，S3 查询已绑定网关的地址及控制端口；服务类型和字段在跨仓库协议中统一定义。mDNS 只负责地址发现，其结果不作为身份认证依据，不在记录中发布密钥。两端须处于可互通的局域网；访客网络隔离或组播受限时应报告发现失败。

建议使用独立 TCP 控制连接，S3 主动发起，UDP 保留传输音频。握手顺序为：

1. 交换设备身份、协议版本和随机挑战，使用绑定凭据进行双向校验。具体报文、密码算法、挑战防重放和密钥存储规则在实施前定义，不自行设计未经审阅的密码协议。
2. 协商采样率、PCM 格式、UDP 端口和音频能力；不支持的组合明确拒绝，不能默认按同一格式解释。
3. 建立新的控制会话和媒体会话/代次，双方确认就绪后恢复转发模式。明确映射现有 HFAP session/generation，不接受旧连接残留包。
4. 控制连接建议每 2 秒心跳，约 6 秒未响应判定离线。这些是初始参数，需通过共存和掉线测试调整。

无论哪块板子先上电，另一端上线后均自动发现和重试。掉线或重启后停止旧媒体、清理缓存并重新握手，IP 改变不需要手动更新 peer。重试使用退避，避免紧密扫描。正常通话期间停止 BLE 配网扫描；控制连接与发现逻辑不能阻塞音频任务。

“音频桥就绪”仅代表控制和传输准备完成，不代表真实双向语音验收通过。手机 HFP/SCO 生命周期和媒体代次还需按第 16 节独立验收。

### 17.5 更换 Wi-Fi、换绑与恢复

- 换网时，用户先使 S3 连接新路由器，再执行 `gateway reprovision`。网关无法连接旧网络约 60 秒后，开启面向已绑定 S3 的 BLE 恢复入口，同时低频尝试旧网络；用户也可长按约 3 秒主动清除 Wi-Fi 配网信息并立即进入重新配网窗口，此后不再尝试已清除的旧网络。窗口超时仍保持无 Wi-Fi 配置，不恢复旧凭据；可再次长按开启窗口。
- 已绑定 S3 必须先验证绑定身份，再通过 BLE 更新网络；无需再次按键确认。换网只更新 Wi-Fi 配置，不清除设备绑定。未绑定设备不得利用恢复入口修改配置。
- 使用候选网络配置进行连接验证，失败保留可恢复状态和错误原因，避免覆盖后失去唯一可用配置；新网络成功后提交配置，再通过局域网重新发现和握手。用户已经通过长按清除旧网络时，不回滚已清除的凭据，失败后保持等待重新配网。
- 换绑另一台 S3 需要网关实体按键重新授权，不能因为旧 S3 不在线就自动接受陌生主机。换绑成功时旧凭据失效。
- 恢复出厂清除网络和绑定，采用区别于普通配网的更长按键操作及明确反馈；具体时长待实现确定，避免误触。清除网关配置不应顺带擦除无关 NVS 或手机蓝牙配对记录，除非另有明确操作定义。

### 17.6 S3 串口调试入口

以下命令为当前调试接口：

| 命令 | 用途 |
| --- | --- |
| `gateway scan` | 限时 BLE 扫描，返回设备 ID、信号强度、待配网/恢复状态及可验证的绑定状态 |
| `gateway provision <设备ID>` | 选择目标，建立会话，等待网关短按确认，同步 S3 当前网络并完成绑定 |
| `gateway status` | 输出当前阶段、两端连接状态及分方向音频统计，不触发重配网 |
| `gateway reprovision` | 对已绑定网关认证后更新为 S3 当前网络 |
| `gateway reconnect` | 非通话状态主动重新发现并握手；通话中返回 busy，避免切断现有音频 |

耗时操作异步执行，有操作 ID、超时和明确的阶段/错误输出。串口处理不阻塞主循环或音频任务；重复请求返回 busy 或明确复用同一操作。通话中拒绝普通扫描、配网和换绑，不隐式中断电话。只在显式调试入口输出必要信息，不能把输入凭据回显到日志。

`gateway status` 至少包括：本机/对端设备 ID、绑定状态、当前操作与阶段、BLE 会话及待按键确认状态、两端 Wi-Fi 状态和当前 IP、发现及身份校验结果、控制连接/最近心跳/断线原因、协商音频格式、媒体会话及代次、转发模式、手机 HFP 和 SCO 状态，以及分方向 UDP 收发、拒包、丢包、迟到、重复、缓存欠载和队列丢弃统计。不能取得的远端字段标为 unknown 或 stale 并带观测时间，不能填成正常或零。链路离线时保留最近错误，但不把过期状态当成实时状态。

后续屏幕可调用同一套配网和状态接口，当前不添加页面、按钮或交互界面。

### 17.10 2026-11-25 mDNS 启动内存不足与重复初始化

首轮还复现主机工具缺陷：它等待 S3 串口导出完成后才请求经典端导出，期间经典端调试缓存按原有有界保留策略过期释放，最终 `PCM_BEGIN bytes=0 goal=0`。因此原报告保持 FAIL，不把空文件认作网关未采集或音频当时没有传输。主机现于 SCO 关闭后先同时发送两端导出命令，再独立等待各自结束和超时，不延长固件缓存存活期。

### 18.23 官方 Wi-Fi 性能参考与双板 PSRAM 预算

用户提供的 [ESP32-S3 Wi-Fi 性能与节能](https://docs.espressif.com/projects/esp-idf/zh_CN/latest/esp32s3/api-guides/wifi-driver/wifi-performance-and-power-save.html#how-to-improve-wi-fi-performance) 可作调参依据；`latest` 内容随 SDK 变化，本轮同时核对本机 IDF 6.1 提交 `fff9895c82d744c7237be8847347bdd1b07c6643` 下同名 RST、`components/esp_wifi/Kconfig`、ESP32/S3 各自 `esp_adapter.c` 与 lwIP `lwipopts.h`。经典 HFP 共存还需读 ESP32 目标文档，不能套用 S3 的 BLE 共存表。

两端有效配置均启用 `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y`、Bluetooth 外部优先分配，普通大块音频/诊断数据按各仓库内存规则外置。SDK 的 Wi-Fi 普通分配和 lwIP 分配使用 PSRAM 优先、内部回退，不能声称全部网络内存都已外置；Wi-Fi 内部/DMA 分配仍显式要求内部能力，任务、锁和描述符另有约束。本轮 S3 PSRAM 空闲约 5.9 MB，但内部空闲仅约 9.5 KB、最大块约 4.6 KB；不能由外部余量推断内部资源充裕。

实际经典 Wi-Fi 接收配置为 static=16/dynamic=32、AMPDU RX 开启、BA window=16；S3 为 static=3/dynamic=6、AMPDU RX 开启、BA window=3。增加 S3 动态接收数量是可单独评估的后续变量，但必须保持有界、确认外部优先策略，并测内部最低/最大块、PSRAM、真实迟到/补帧和延迟。静态 DMA 缓冲不能仅因为 PSRAM 充裕而直接全部外置或大幅增加；不照搬文档 iperf 吞吐量档位，不盲目打开增加 IRAM 占用的优化，也不为 UDP 音频扩大无关 TCP 窗口。

当前 bridge 在会话期间读回日志为 Wi-Fi `PERFORMANCE (NONE)`；官方说明关闭 modem sleep 可以减少节能引入的接收延迟，但共存射频时间片限制仍存在。socket 字节限额、UDP 邮箱、Wi-Fi 动态/静态接收缓存和播放抖动缓存属于不同层，分别验证。使用 PSRAM 的目标是承接有界突发并保留内部 SRAM；不能通过无限缓存积累过期音频，更不能修复进入 UDP 前已缺失的 HFP 声音。

### 18.26 2026-11-27 Android UART 链路复测与握手修正

使用同一部 Huawei ATU-AL10 Android 真机重新运行 30 秒 mSBC 双向测试。经典 ESP32 在 SCO 建立后成功关闭 Wi-Fi，最新一轮统计为 `sco_rx_total=4051`、`sco_rx_correct=4023`、`sco_rx_none=28`、`sco_rx_err=0`，缺帧约 `0.69%`，继续满足 1% 目标；Android 录音/播放线程持续到 `duration_complete`。但 S3 串口仍记录 `wire bytes=0 frames=0`，上行录音 RMS 为 0，完整链路按 UART 传输规则判定失败。

当前实体接线必须明确为 3.3V TTL、共地：经典 ESP32 `GPIO25/TX -> S3 GPIO0/RX`，S3 `GPIO43/TX -> 经典 ESP32 GPIO26/RX`，并连接 `GND`。S3 排针标注的 `ESP_RXD` 是 GPIO44，而 GPIO44 当前承担 ES8311 MCLK，不能把它当作本实现的 UART RX；若实际接在该标注脚，S3 仍会显示 `wire bytes=0`。在物理字节、HELLO/ACK、UART CRC 和上下行媒体计数均连续后，才继续 5 分钟、ASR 和 30 分钟长稳验收；ESP-NOW 暂不切换。
