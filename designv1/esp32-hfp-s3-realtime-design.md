# ESP32 HFP 电话网关与 ESP32-S3 Realtime AI 双芯片设计

日期：2026-11-18

状态：已开始 P0/P1/P2 实施。独立网关仓库已创建，经典 ESP32 固件已构建、烧录并与 Windows 建立 HFP；S3 电话桥已接入并完成 Wi-Fi/UDP PCM 联调。当前已验证 mSBC / 16 kHz 与 CVSD / 8 kHz 的解析路径、S3 侧 8/16 kHz 重采样和 5 分钟 UDP 连续接收。真实手机通话、反向麦克风自动采集和完整 Wi-Fi/蓝牙共存听感仍待验证。本文带宽是计算值，后续时延与兼容性指标仍为目标。

## 1. 目标与架构

用初代 ESP32 连接手机的蓝牙通话音频，用 ESP32-S3 承担阿里云 Realtime 会话。远端来电人的声音进入 AI，AI 回复通过手机发送给远端，实现电话中的 AI 对话。

```text
远端通话人 ↔ 运营商电话 / 手机 VoIP 应用
                          ↕
                    手机（HFP AG）
                          ↕ Bluetooth Classic HFP / SCO 或 eSCO
                 初代 ESP32（HFP HF）
                          ↕ 局域网 UDP，双向 PCM / ADPCM / Opus
                 ESP32-S3（Realtime 主机）
                          ↕ TLS / WebSocket，按模型要求传 PCM
                    阿里云 Realtime
```

“电话网关”是本系统的用途名称。蓝牙协议角色应为 **ESP32 = HF / Hands-Free Client，手机 = AG / Audio Gateway**，不能因为名称叫网关而选用 `hfp_ag` 示例。[S1]

初代 ESP32 提供本方案所需的经典蓝牙 HFP；ESP32-S3 只有 Bluetooth LE，不能直接替代经典蓝牙 HFP 端点。两颗芯片的分工以此为基础，不能把 BLE 或 A2DP 当成双向电话音频的直接替代。[S1][S2]

首版只连接一部手机、处理一路通话。2026-11-18 增加普通电话来电指示后延迟 3 秒自动接听；复杂通话保持、多手机切换和全双工插话放到后续独立评估。

开发阶段先以 Windows 电脑代替手机充当 HFP AG，通过固定 WAV 播放与录音验证双向音频，再逐步加入 UDP、S3 和云端。真实手机通话与微信兼容性在后期单独验收，日常音频调试不要求反复拨打电话。

## 2. 两端职责与工程边界

| 端点 | 职责 | 首版约束 |
| --- | --- | --- |
| 初代 ESP32 | 手机配对、HFP 状态、SCO 音频收发、局域网音频桥、计数器 | 不承担 TLS 云连接、AI 或复杂 UI；不预设具有 PSRAM |

## 3. HFP 音频获取与数据流

### 3.1 HFP 数据路径

优先选择 HCI/vHCI 音频路径，在应用层桥接音频；不把控制器 PCM 引脚路径误认为已自动进入 UDP。官方示例区分这两种路径，并提供 CVSD 与 mSBC 的配置说明。[S1]

首版在内部统一为单声道 PCM16，再做局域网编码。CVSD 通话按 8 kHz PCM、mSBC 宽带通话按 16 kHz PCM处理；实际启用的编码必须由协商事件与数据路径验证，不以“支持宽带”或手机支持 VoLTE 推断已经使用 mSBC。[S1]

特别注意 IDF 6.1 官方示例存在内部编解码的旧式 PCM 回调路径，以及 `CONFIG_BT_HFP_USE_EXTERNAL_CODEC` 下的新音频缓冲回调路径。后者可能交付 mSBC 编码载荷，不能把所有 HCI 回调内容都解释为 PCM16。阶段一须确认选用路径、帧格式、缓冲所有权和释放时机；选外部编解码时必须补全对应解码/编码。[S3]

蓝牙回调只执行有界复制或缓冲所有权转移和队列通知；UDP、Opus、重采样及日志写盘在工作任务运行。发送失败和队列满要有明确回收与丢帧计数，不能阻塞蓝牙栈。

### 3.2 手机声音进入 AI

1. 手机将远端通话声音经 SCO/eSCO 发送到 ESP32。
2. ESP32 获得或解码为 HFP 原生采样率 PCM，按 20 ms 组帧。
3. ESP32 编码局域网载荷，携带序号、样本时间戳和会话代次发送 UDP。
4. S3 通过抖动缓存恢复时间顺序，解码并转换到云端输入采样率。
5. S3 将 PCM 按现有 Realtime 协议上传，由手动提交或云端 VAD 完成分轮。

### 3.3 AI 回复进入电话

1. S3 收到云端回复 PCM，根据实际模型会话确定采样率。
2. S3 重采样到 HFP 协商采样率，按局域网格式编码发送。
3. ESP32 经抖动缓存和解码后，按蓝牙发送节拍填充 HF 麦克风方向音频。
4. 手机把这一路作为蓝牙麦克风输入发送给远端通话人。

局域网 Opus 与 HFP mSBC/CVSD 是独立编码层；首版不直接透传 mSBC 到云端。Opus 解码后才转换为云端要求的 PCM，不假定阿里接口接受任意 Opus 裸包。

云端先沿用现有集成的格式，目标基线为输入 16 kHz、输出 24 kHz、单声道 PCM16。阿里官方不同模型/SDK的采样率配置能力有差异，实施时固定模型和配置，不能将该基线写成所有 Realtime 模型的统一限制。[S4]

## 4. PCM、ADPCM、Opus 带宽比较

以下均为单声道、单方向，`kbit/s = 1000 bit/s`。以 20 ms 一包计算，每方向 50 包/秒；IPv4+UDP 为 28 字节，再假设自定义头 32 字节，则每方向固定增加 24 kbit/s。未计 Wi-Fi MAC/PHY、加密、ACK、竞争退避及重传。

| 局域网格式 | 采样率 | 音频有效载荷 | 每包音频字节 | 加上述头部后单向 / 双向 |
| --- | --- | --- | --- | --- |
| PCM16 | 8 kHz | 128 kbit/s | 320 | 152 / 304 kbit/s |
| PCM16 | 16 kHz | 256 kbit/s | 640 | 280 / 560 kbit/s |
| PCM16 | 24 kHz | 384 kbit/s | 960 | 408 / 816 kbit/s |
| 4 bit IMA ADPCM，理想载荷估算 | 8 kHz | 32 kbit/s | 80 | 56 / 112 kbit/s，另加块状态 |
| 4 bit IMA ADPCM，理想载荷估算 | 16 kHz | 64 kbit/s | 160 | 88 / 176 kbit/s，另加块状态 |
| Opus，拟定固定目标码率 | 8 / 16 kHz 输入 | 16 kbit/s | 约 40 | 约 40 / 80 kbit/s |
| Opus，拟定固定目标码率 | 8 / 16 kHz 输入 | 24 kbit/s | 约 60 | 约 48 / 96 kbit/s |

计算公式：PCM 码率 = 采样率 × 16；ADPCM 理想码率 = 采样率 × 4；包开销 = 60 × 8 × 50。ADPCM 的预测器和步长索引等块状态会增加实际码率；Opus 若使用 VBR、FEC 或改变帧长，实际包长也会改变。上表不是实测网络吞吐或射频占用。

建议先用 PCM 建立正确性基线，再测试逐包独立状态的 IMA ADPCM，最后以 **16 kHz 单声道、20 ms、16–24 kbit/s Opus** 作为候选正式格式。Opus 支持交互语音和 20 ms 帧，但初代 ESP32 上的编解码 CPU、内存与时延必须实测后决定。[S5]

Opus 可降低传输字节，不能承诺同比降低 Wi-Fi 空口时间；小包下固定开销占比显著。ADPCM 的每包应独立携带恢复状态，避免一次丢包污染后续整段音频。禁止用“ADPCM”名称代替明确的编码格式、块布局和互通测试。

## 5. UDP 与 Bluetooth 共存

UDP 是传输协议，实际链路仍使用 ESP32 的 2.4 GHz Wi-Fi。初代 ESP32 的 Wi-Fi 与 Bluetooth 共用射频并采用时分仲裁，因此“改成 UDP”不能消除与 SCO/eSCO 的竞争。[S6]

首版拓扑建议两颗芯片都以 STA 接入同一个外部 AP。初代 ESP32 通话时避免扫描、配网、OTA和大流量诊断；启用软件共存，按官方建议评估 Wi-Fi 与蓝牙任务分核运行。不要未经测试就修改底层共存优先级。[S6]

外部 AP 转发意味着一次芯片间单向传输通常经过 STA→AP、AP→STA 两段无线发送；带宽表仅计算 IP 流量，不能直接当成空口预算。S3 还需访问云端，测试须把其真实云流量一并纳入。

S3 SoftAP + ESP32 STA 可作为独立对照拓扑，但 S3 的 STA 上网与 SoftAP 信道约束、转发路径、断网行为必须单独验证，不把它当成天然更稳定的方案。两颗芯片使用独立射频也仍可能互相干扰，天线距离和供电需实测。

先分别测 HFP 单独运行、HFP+空闲 Wi-Fi、HFP+双向 PCM、HFP+ADPCM、HFP+Opus，再加入云端流量和弱信号。记录坏 SCO 帧、丢包、迟到包、欠载、CPU 与内部堆余量，区分射频损伤与任务处理不及时。

若压缩、限流和调度优化后仍不能达标，保留有线 SPI/UART/数字音频桥接为备选。它是后续决策分支，不能在未评估接线、时钟、电平及新板身份前直接实施。

## 6. UDP 包、控制与会话隔离

以下为拟定协议字段，阶段二需明确字节偏移、网络字节序和版本兼容规则，再编码实现：

| 类别 | 必需信息 |
| --- | --- |
| 包识别 | magic、版本、头长、载荷长、音频/控制类型 |
| 会话隔离 | 启动标识、通话代次、媒体方向；取消时额外递增回复代次 |
| 音频解释 | codec、采样率、单声道标志、每帧样本数、编码附加状态 |
| 排序与播放 | 每方向独立序号、源样本累计时间戳、流重置/静音标志 |

32 字节只是带宽计算的占位预算；字段落定后重新计算。不要原样发送带填充的 C struct。限制 UDP 数据报总长不超过 1200 字节，超过即拒绝或重新设计帧长，不依赖 IP 分片。

媒体不重传过期音频，丢帧后做 PLC 或短静音并计数。控制消息使用命令 ID、确认、超时和有界重试，接听、挂断、重置应幂等；同一条接听命令重试不能变成第二次操作。

建立会话握手后才接受媒体，验证来源、长度、codec、采样率、帧样本数和代次；重启、断线、挂断、取消回复时清空对应队列和解码状态。生产版本须定义配对认证和防重放机制；单靠来源 IP 只适合受控原型，不算身份认证。

## 7. 重采样、节拍与抖动缓存

HFP 原生 PCM 与局域网传输优先保持同一采样率，重采样集中在 S3 的云端边界：电话 8/16 kHz → 云端输入 16 kHz；云端输出 24 kHz → 电话 8/16 kHz。若模型使用其他格式，以实际协商配置为准。

降采样必须使用抗混叠滤波；升采样不会恢复窄带电话已丢失的频谱。采用流式、有状态的重采样器，帧间保留滤波状态，不逐包重置。

每方向独立设置抖动缓存，初始目标 40–60 ms，可在 20–100 ms 范围内调整；超过最大音频年龄的包丢弃，不能为追求零丢包而无限增加延迟。序号处理乱序和重复，样本时间戳驱动播放节拍。

两颗芯片和蓝牙时钟可能有长期频偏。持续监控缓存水位和累计样本差，用缓慢自适应重采样或有平滑处理的样本修正消除漂移；禁止每隔数秒粗暴丢掉一整帧而不记录。

单个 16 kHz PCM16、100 ms 缓存约 3.2 KB，两方向约 6.4 KB；这仅是解码后音频，不包含 Opus 状态、蓝牙/Wi-Fi 栈、队列和任务栈。初代 ESP32 内部堆最小余量与最大可用块必须在完整负载下测量。

## 8. 电话轮次、取消与故障恢复

首版沿用现有 [Manual / Auto 设计](aliyun-manual-auto-design.md) 的半双工原则：AI 回复期间不向云端上传远端讲话；回复结束且电话发送路径本地待发音频排空后恢复监听。播放期间仍及时消费 HFP 接收数据并丢弃，不积压到下一轮。

本地队列排空仅说明桥接端已送交蓝牙栈，不能证明远端已听完。恢复等待需结合 SCO、手机和通话链路测量。HTTP/串口日志的“发送完成”不能写成远端实际播放完成。

电话音频作为数字源时，首版不套用本地麦克风 NSNet/AFE/AEC。数字桥减少本地扬声器声学回授，但远端免提回声、手机或网络侧回声仍需验证。全双工插话、远端说话打断 AI 和回声抑制作为后续专题；本地唤醒词打断结论不能直接套到电话音频。

收到挂断、HFP 音频断开或链路超时后，停止该代上行、取消云端回复、清空两端媒体，拒绝旧代迟到数据。云端断线时停止向电话注入旧音频，并明确显示不可用状态，不在无确认的情况下循环自动拨号或接听。

S3 应用状态通过 `Application::Schedule()` 回到主任务，并由 `SetDeviceState()` 与状态机管理。电话链路状态与 AI 轮次分别记录，避免把“蓝牙已配对”当成“音频已接通”。

## 9. 普通电话与微信等 VoIP 的兼容边界

### 9.1 Windows 电脑优先调试

Windows 在 HFP 中可承担 AG，ESP32 仍承担 HF。Windows 支持 HFP 单声道同时播放与录音，因此日常测试可直接由电脑提供测试语音、接收返回音频，无须建立真实电话。[S8][S9]

```text
电脑播放固定 WAV → HFP → ESP32 → UDP → S3 → 阿里 Realtime
电脑录制返回 WAV ← HFP ← ESP32 ← UDP ← S3 ← 阿里 Realtime

电脑 USB → ESP32：供电、烧录、串口日志
```

| 电脑上的音频操作 | ESP32 侧方向 | 电话场景对应含义 |
| --- | --- | --- |
| 向 ESP32 对应的 HFP 播放端点写入 WAV | HFP 接收，随后向 S3 上行 | 远端通话人讲话 |
| 从 ESP32 对应的 HFP 录音端点读取 WAV | HFP 发送，承载 S3 下行 | AI 向远端通话人回复 |

USB 连接本身不作为本方案的 HFP 音频路径。2026-11-18 已在 Windows 10 / Intel 蓝牙上完成配对、HFP SLC、CVSD 与 mSBC 双向短测；详细验收与失败记录见第 11 节及独立网关实施记录。

Windows 10 可显式选择 Hands-Free 播放/录音端点；Windows 11 可能统一端点名称，打开该设备的麦克风输入可使系统选择 HFP。测试工具需保持输入与输出同时打开，显式记录端点 ID，不能只看“已连接”或播放设备名称认定在走 HFP。[S8]

HFP 音频连接不应依赖真实通话状态；固件须处理电脑 AG 在空闲状态发起的音频连接。[S9] 实施时以 ESP32 日志中的 SLC、SCO/eSCO、实际 codec 和收发计数为证，记录 Windows 版本、蓝牙适配器、驱动版本及所选端点。电脑 API 的音频格式可能经过系统重采样，不能用 WAV 的采样率反推 HFP 编码。[S8]

先确认 CVSD 路径可用，再验证 mSBC。若本机驱动或设备组合无法协商宽带，先记录为窄带通过、宽带未通过；不能把勾选宽带配置当成 mSBC 验收。若本机 HFP 无法建立，先排查服务声明、配对、驱动和音频连接状态；必要时以一部手机作对照定位，不能用 A2DP 或 USB 音频结果替代 HFP 验证。

电脑测试工具按以下顺序建设，放在新网关仓库的 `tools/` 下：

1. 枚举并选择蓝牙播放/录音端点，播放固定 WAV、录制返回 WAV，保存串口日志及测试元数据。
2. 在 ESP32 的 HFP 接收端保存短时有界 PCM 样本，发送方向独立注入测试音，先分别证明两条路径。环回仅作为明确开启的诊断模式，正常模式不把输入直接反馈输出。
3. 加入 S3 后，使用相同测试素材和参数验证 UDP 桥，再加入真实云端流量比较 PCM、ADPCM 和 Opus。
4. 接入 Realtime 后，固定问题集、重复次数、轮间等待和超时，自动保存每轮输入、回复、状态及失败原因，生成结果摘要。

首批测试素材包含静音、短测试音、中文短句和长句。先从较低音量确认无削波，并记录系统音量和音效设置；录制阶段避免把返回声音再次送入测试输入形成回授。音频环回成功不代表语音识别和对话正确，自动化结果仍需结合文本及录音抽查。

电脑验证覆盖 HFP 双向媒体、UDP、编码、共存、重采样、云端轮次和长稳测试；手机真实来电事件、AT 接听挂断、运营商链路、微信路由和远端回声仍必须通过手机验收。

### 9.2 手机与应用验收范围

| 场景 | 预期与边界 | 验证方法 |
| --- | --- | --- |

每阶段保留样本数、分位数、测试时长、丢包与坏帧分母、队列峰值、堆最小值、复现步骤和固件哈希。采集点至少包含 HF 入站 PCM、云端上行 PCM、云端下行 PCM、HF 出站 PCM；这些仍不等于手机远端真实播放录音。调试抓取要限流、有界，单列其对共存性能的影响。

1. 手机连接 `ESP32-HFP-Gateway` 后，让另一部手机呼入。

## 15. 2026-11-18 实际手机杂音后的修复与电脑声学验收

### 15.1 已定位问题与代码调整

- S3 的 8K/16K → 24K 线性插值曾混用有符号差值和无符号插值权重，使下降沿发生整数回绕；现统一使用有符号计算，并在启动时检查两种输入率的正负满幅交替样本。
- FreeRTOS 为 100 Hz 时 `pdMS_TO_TICKS(2)` 等于零，桥接空转曾触发 `IDLE1` 看门狗；现每轮至少等待一个 tick，包括重复包和无效包分支。
- 连续 PCM 播放曾在队列暂空时等待整个 60 ms DMA 尾部；PCM 桥接模式不再采用该有限音频播放等待。
- 桥接开始和新媒体会话时通过 Board 接口切到 Wi-Fi PERFORMANCE，避免启动完成后的省电状态继续影响通话。
- S3 起播先缓存 4 个 20 ms 帧，即 80 ms；会话变化或接收间断超过 200 ms 时重新起缓冲。这是有限起播缓存，尚不是完整的乱序、丢包补偿和时钟漂移校正器。
- S3 日志增加 `seq / gaps / reordered / queue_drops / max_gap_ms`；其中 gaps 为按到达顺序观察到的序号缺口，不能当成经过等待和重排确认后的最终网络丢包率。
- 网关只对经过 H2/mSBC 同步检查的帧调用正常解码，移除猜偏移直接送解码器的兜底；补偿帧正确标记为 concealed。
- 网关增加外部编解码配置的编译检查，避免内置 HFP 编解码与应用层 SBC 实现同时启用。

### 16.2 新增自动拦截

网关 `tools/phone_log_audit.py` 离线读取同轮两板日志，检查每通电话的 peer 证据、Wi-Fi/转发、HFP 状态/采样率/代次、双向计数逐段推进、S3 同时段 RX/TX。通话中状态丢失、代次反复变化、计数停止、错误或损失增量、数据缺失均阻断；没有电话或观测不足默认 60 秒也不能通过。少量无线损失会触发保守复核，初筛通过不证明真实音质。

输出仅为 `transport_log_screen_passed`，`full_duplex_speech_passed` 和 `phone_call_lifecycle_passed` 保持 null。报告绑定输入日志 SHA256 并拒绝覆盖。现有 `phone_bridge_bench.py` 的 `passed` 只属于所标的下行/环回/本机声学单项。

### 16.3 后续放行顺序

1. 保存新固件身份和原始启动状态；地址、工作模式、采集日志均核对后才进入媒体测试。历史脚本中的隐式配置不能代替启动验收。
