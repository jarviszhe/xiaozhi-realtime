## 1. 目标与依据

将现有双板无线电话桥、阿里语音能力和屏幕设计接成完整流程：

屏幕配网 → 手机连接 → 来电接听 → AI 对话／人工接管 → 保存录音与通话记录 → 回看文字和播放录音。

- [最终版界面总览](../design/最终版/README.md)：当前采用的 9 张页面／弹窗，目标为 480 × 320 横屏触摸彩屏。
- [界面交互需求](../design/界面设计.md)：页面行为、异常状态、录音、规则与待确认事项。
- [内存分配规则](../docs/memory-allocation.md)：PSRAM、内部 SRAM 和音频任务约束。

经典 ESP32 代码位于 `D:\work\Bluetooth-gateway`，负责手机 HFP、呼叫控制、无线媒体桥和网关状态。S3 代码位于 `D:\work\xiaozhi-realtime`，负责屏幕、阿里会话、音频路由、录音、记录与规则。跨仓库媒体和管理协议分别以网关仓库 `docs/protocol/udp-audio-v1.md`、`docs/protocol/gateway-management-v1.md` 为权威定义。

## 2. 当前基线与缺口

两端已恢复 UDP 并烧录，经典 ESP32 在 SCO 活动期间保持 Wi-Fi 开启；当前上行使用 IMA ADPCM、下行使用 PCM。UART 保留为未来实验方向，Opus 尚未接入，不作为已经验证的修复。

第 18.28 节 Android 测试已完成原始／接收录音、ASR、候选低能量和 UDP 统计。两轮上行接收 ASR 字符差异为 3.45% 和 0%，首轮还有 272 个越窗拒包；蓝牙原始坏帧约 9.06%–9.59%。下行数字录音 ASR 零差异，但声学拾音弱，扬声器清晰语音尚未验收。应用端 UDP 收发差额不等于抓包确认的纯网络丢包率。

现有网关自动配网和阿里语音各有实现基础，电话音频尚未正式接入 AI 电话闭环。界面目录仍为静态设计；页面所需的来电号码、倒计时、接听结果、录音保存结果等，还需建立完整接口。当前诊断 PCM 抓取不能直接作为长期通话录音功能。

### 阶段一专项任务 B：补齐 S3 扬声器声学验证

下行分四个观测点确认：手机实际播放 PCM → 经典 ESP32 HFP 解码录音 → S3 送入音频 codec 前 PCM → S3 扬声器前的声学录音。前三个点用于确认数字数据，最后一个点才检验实际扬声器的可听输出与连续性。测试前固定 S3 音量（当前基线为 60%）、电脑录音设备和增益，保存静音／峰值／削波状态；先播放已知频率短音校准麦克风位置和输入电平，再播放同一组中文语音。不能用弱拾音的声学文件直接判定喇叭故障，也不能用 S3 codec 前 ASR 正确替代声学验收。

声学录音必须同时记录环境噪声基线、目标信号 RMS／峰值、削波比例、目标频带信噪比和录音设备信息。若录音电平过低，先调整麦克风距离、输入增益或测试音量并重新记录；不得用事后数字放大把噪声当成有效播放。声学语音和数字源使用同一段已知语料，分别比较 ASR 字符差异、源活动覆盖、候选低能量累计量及最长连续时长；保留对齐可信度和无法覆盖的尾部。

专项 B 的验收分两步：先用已知频率确认声学目标信号持续存在且高于噪声，随后用同源中文语音确认声学录音可识别、无持续单向无声或明显断句。数字路径 ASR 为 0 只能记作数字链路通过；声学录音仍需达到可解释的信噪比和语音识别结果，才可将“下行扬声器可靠声学验证”记为通过。若电脑麦克风仍无法取得可信声学信号，则记录为声学测量 BLOCKED，同时保留数字链路结果，不能写成扬声器通过或失败。

#### 阶段一两个专项的实施与判定记录（2026-11-27）

专项 A 的实现验收是：活动语音窗口内每个 `WINDOW` 结果都能由序号、队列和代次解释；启动／停止尾包单独计数；同条件复测不再出现无法解释的连续越窗；修复后完成一次 5 分钟双向运行，并保留 `gaps/PLC/rebuffer/max_gap`、HFP 坏帧和 ASR 对照。只要还有无法解释的窗口拒包，专项 A 仍为 FAIL。

**专项 B：S3 扬声器声学验证的实施记录。** 本轮使用 Android 已知下行语音，保存网关 HFP 解码 PCM、S3 codec 提交前 PCM 和电脑麦克风声学 WAV，测试时关闭电脑扬声器，S3 音量固定为 60%，并用同一份参考语料和阿里 ASR 进行比较。产物目录为 `D:\work\Bluetooth-gateway\artifacts\android-speaker-acoustic-phase1b-20261127-01`。

首轮 `android-speaker-acoustic-phase1b-20261127-01` 的网关解码录音约 59.90 s、S3 codec 前约 59.94 s，二者 ASR 与同模型参考的 109 字均为 0 编辑差异；这只证明本轮语料可完整识别到 S3 播放前，不证明数字时序或扬声器听感全部通过。电脑声学录音约 62.36 s，原始 RMS 为 81.8，峰值为 2593；归一化后 ASR 仍有 34/109 字差异（31.19%），出现漏词和错词，声学验收未通过。其信号偏弱可能来自声学耦合、录音处理或播放端，需要校准区分，不能据此归咎于某个硬件。

### 阶段二：建立电话状态与控制接口

当前交付与实测：见[阶段二实现和验证报告](phase2-phone-control-validation-20261127.md)。两端已烧录；Android 本地通话 11 项检查通过，自动接听实测 3132 ms。此结果只覆盖电话状态／控制，不提升阶段一音质验收状态。

扩展两端认证控制通道，支持来电号码或未知来电、呼叫状态、实际接通／结束事件、自动接听状态和倒计时。补充 S3 发出的接听、拒接、挂断命令及确认、超时和错误反馈。

本阶段采用已有签名 TCP 39002，保持每包 128 字节。双方协商电话扩展后，S3 每 500 ms 发送 `PING`，携带命令、请求序号和目标通话 ID；经典端只执行新序号一次，`PONG` 返回 ACK／结果、呼叫指示和接通时长，再发送同样经过 HMAC、双端 nonce 与心跳序号校验的 type 7 电话状态包。状态包含通话 ID、版本、来电号码、阶段、实际接通／结束时间和倒计时。旧固件仍可运行原媒体桥，缺少新鲜电话状态时 S3 拒绝控制命令。协议权威定义见网关仓库 `docs/protocol/gateway-management-v1.md`。

S3 同时只保留一个待确认请求，5 秒超时；断开立即终结未确认请求，重连后不重放。接听、拒接／挂断、取消倒计时绑定当前通话 ID，防止作用到下一通。ACK 只表示 HFP API 接受请求或返回错误，接通／结束必须等待真实 HFP 指示；AT 结果仅作为独立诊断。通话计时由经典端实际接通／结束事件计算，S3 在状态新鲜时外推显示，SCO 关闭不暂停计时。

两端串口均支持 `phone help`、`phone status`、`phone answer`、`phone reject`、`phone hangup`、`phone audio on|off`、`phone auto on|off|cancel`。经典端保留旧命令。`auto cancel` 只取消当前来电倒计时；`auto off/on` 是本次运行策略，默认仍为 3 秒自动接听，打开策略不会重新启动已经取消的当前倒计时。`audio off` 禁止当前通话自动重建 SCO，`audio on` 恢复。`PHONE` JSON 和 `PHONE_EVENT`／`PHONE_COMMAND_END` 日志用于追踪新鲜度、通话 ID、号码、阶段、计时、倒计时、请求和结果。蓝牙坏帧只作为诊断字段，不作为本阶段控制接口验收阻塞项。

验证工具为网关仓库 `tools/android-call` 和 `tools/phone_control_bench.py`。Android 使用受系统 Telecom 管理的本地 ConnectionService，产生实际 HFP 来电／呼叫指示；模拟呼出仅使用固定 `sip:gateway-test@example.invalid` URI 和测试账户，由本地服务处理，不拨打 SIM 电话。自动化保存两板原始串口、Android 回调及主机时间线，检查手动接听／拒接／挂断、3 秒自动接听、取消倒计时、已知／未知号码、SCO 开关、手机主动接听／结束、本地呼出、无通话非法操作、HFP 断线和控制重连。不能以 `am start`、命令 ACK 或 SCO 建立替代实际呼叫指示。

统一通话标识、状态和命令幂等处理；界面订阅状态，按钮发出请求，不能仅凭按钮点击更新为“已接通”。已有约 3 秒自动接听需要纳入统一策略，避免经典端仍独立无条件接听。区分通话实际接通与 SCO 媒体就绪，处理铃声先建 SCO、接听后建 SCO、对方取消、手机端接听及断线。

本阶段验收要求：重复命令不产生重复 AT/HFP 操作；每个命令有明确序号、ACK、结果和超时；断开／重连不重放旧命令；`call_setup`、`call_active`、SCO 状态能够分别观察；3 秒自动接听在 Android 场景可追踪；倒计时可以取消；界面时间与真实通话事件一致；号码不可用时显示未知来电。协议变化同时更新两端实现、兼容定义、串口命令说明和测试向量。电话音质、蓝牙坏帧和完整运营商生命周期仍在后续验收。

## 5. 界面补齐与实现边界

九张设计稿之外，还需实现接听中、人工接管确认、人工通话、结束保存反馈、语音规则核对，以及加载、空数据、取消、超时和各类错误状态。这些是现有设计需求中的必要状态，不能因为没有单独视觉稿而省略。

页面使用真实状态模型与事件驱动更新，不在绘制回调里执行扫描、网络请求、ASR 或文件写入。应用状态更新回到主任务，沿用 `Application::Schedule()`、`SetDeviceState()` 和状态机；核心层通过接口访问可选屏幕、存储等能力，不依赖具体板型引脚。

LVGL、转写列表、音频与存储缓存采用有界设计，符合条件的大块普通数据优先 PSRAM；内部 DMA、ISR 数据、任务栈与系统对象按能力约束审查。转写和通话记录分页／增量加载，不因通话变长无限扩大内存。内存失败记录申请量、能力、内部最低／最大块和 PSRAM 情况，并在全部功能开启时验证。
