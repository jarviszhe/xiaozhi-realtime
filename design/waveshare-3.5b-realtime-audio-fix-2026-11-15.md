# Waveshare 3.5B Realtime 音频问题整理与结论

日期：2026-11-15  
设备：Waveshare ESP32-S3 Touch LCD 3.5B，ES8311，240 MHz，PSRAM  
固件提交：c3645c796bb18670a70440b253fe6d504600e2f2  
SDK：ESP-IDF release/v6.1

## 1. 本次复现的问题

设备测试中出现过以下现象：

- 原始输入 PCM 左声道约 1 分 06 秒，而上行 PCM 1 约 50 秒，语音中间有漏字。
- 长时间播放服务器回复时偶发卡顿、播放速度异常，最后提前没有声音。
- 设备播放声音时近端讲话，句首或短词容易被 AEC 抑制。
- 原始输入轨能够听到完整语音，但经过 AEC 后的上行轨会出现缺字。

原始输入 PCM 位于 ES8311 采集和重采样之前，上行 PCM 位于音频引擎、编码和发送队列之后。因此两者时长不一致主要说明实时上行或队列链路发生了丢帧，不能直接说明 ES8311 没有采到声音。

## 2. 上行和长回复链路的修复

本次代码修改已经提交到 Git，并在设备上完成构建、烧录和长回复验证。主要处理如下：

- 扩大上行编码队列和发送队列，给短暂的主任务或 Wi-Fi 调度抖动留下缓冲。
- 编码任务优先处理麦克风上行，避免长回复解码占用时导致上行等待。
- Application 主任务每次最多发送 16 帧，并在队列仍有数据时继续触发发送事件。
- 发送队列保持有界，队列满时丢弃最旧帧并记录丢帧计数。
- 复用输入缓冲，减少音频实时任务中的重复分配和复制。
- 对云端 24 kHz PCM delta 减少不必要的小包拆分，并同时按包数和 PCM 字节数限制解码队列。
- 与 DAC 采样率相同的 PCM 直接保留接收包，降低长回复期间的复制和解码开销。
- 播放任务继续按不超过 20 ms 的小块写入 codec，并在每块写入前检查播放代次，保证打断后不会继续播放旧回复。
- /api/test/stats 增加上行、下行、播放、编码、AEC 和队列统计，便于判断声音在哪一层丢失。

验证结果表明，修复后长回复会话的上行 PCM 时长已经接近完整会话时长，AFE Feed/Fetch 没有错误，长回复解码入口也不再因为大量小包快速耗尽而丢包。

## 3. AEC 结论

经过多轮设备试听和参数调整，本板的 AEC 效果仍然不稳定，尤其是在设备扬声器播放较强、用户同时讲话的双讲场景：

- 播放参考信号较强时，AEC 会把近端语音误认为回声。
- 句首、轻声词和短词最容易被抑制，表现为“说了一整句但上行只剩半句”。
- 降低播放音量、调整 AEC NLP 等参数可以改变漏字概率，但无法在当前硬件摆位和声学条件下稳定解决。
- 直接混合原始麦克风恢复近端语音可以减少部分漏字，但会带回更多扬声器回声，难以同时满足清晰度和回声抑制。

因此当前结论是：**Waveshare 3.5B 这个板型暂时不启用设备侧 AEC。** 后续如果要重新启用，需要先改变硬件声学条件，例如麦克风和扬声器布局、腔体隔离、扬声器指向性或增加更合适的硬件回声参考。单靠继续微调软件阈值，无法得到稳定的产品效果。

关闭 AEC 后，Realtime 对话仍保留正常的麦克风采集、降噪、VAD、编码和服务器交互；代价是设备播放期间近端麦克风可能再次采到一部分扬声器声音，产品侧应通过半双工策略、播放时降低采集灵敏度或改善硬件声学隔离来控制。

## 4. 降噪效果结论

本板当前最值得保留的处理是 ESP-SR NSNet2 降噪。实测中，降噪效果明显优于只依赖原始 AEC 或简单调低输入增益的方案：

- 安静段的底噪明显下降，类似电流声的连续噪声得到较大抑制。
- 人声主体和辅音仍然保留，正常说话的可懂度没有明显下降。
- 与原始输入相比，降噪后的语音更适合送往服务器识别，短句和轻声内容的背景干扰更少。
- 降噪作用在语音处理链路中，不改变原始 PCM 诊断轨；因此可以同时保留“硬件实际采到什么”和“算法送给服务器什么”两条轨道。
- 降噪对持续底噪、风噪和宽带电流感噪声有效，但不能修复硬件供电、地线、麦克风偏置或扬声器串扰造成的根本问题。
- 降噪不会凭空补回已经被 AEC 删除的语音，因此 AEC 和 NS 的效果必须分开评价。

当前推荐的音频处理链为：

~~~text
ES8311 原始输入
  -> 重采样
  -> NSNet2 降噪
  -> VAD / 唤醒词
  -> Realtime 上行编码
~~~

在这个板型上，宁可保留较小的残余背景噪声，也不要为了追求更强的回声抑制而牺牲近端语音完整性。降噪后的语音完整、稳定、可识别，是当前比 AEC 更可靠的产品基础。

## 5. 诊断和后续测试建议

网页统计应重点观察：

- pcm_accepted_samples 与 pcm_written_samples：判断上行是否有样本缺口。
- send_queue_drops、encoded_frames 和 encode_errors：判断编码和发送阶段是否丢帧。
- decode_drops、queued_pcm_bytes：判断长回复是否仍在下行排队阶段丢失。
- AFE Feed/Fetch 错误：判断降噪处理是否出现实时性问题。
- 原始 RMS 与降噪后 RMS：判断降噪是否过度压低人声。

后续验收应以以下场景为主：

1. 关闭 AEC，开启 NSNet2，验证安静环境、风噪环境和持续电流声环境下的人声完整性。
2. 设备播放服务器回复时继续讲话，确认上行不再因为 AEC 误判而漏掉句首。
3. 连续播放长回复，确认播放队列能够排空，速度和音调保持正常。
4. 重新评估半双工或播放期间采集增益策略，控制关闭 AEC 后的扬声器回采。
