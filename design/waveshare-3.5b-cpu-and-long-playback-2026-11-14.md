# Waveshare 3.5B Realtime CPU 优化与长回复播放排查

日期：2026-11-14。基线：`0016372cd701424021d4707f4c8391fc192f60fb`。
硬件：Waveshare ESP32-S3 Touch LCD 3.5B、ES8311、240 MHz、PSRAM。
SDK：ESP-IDF release/v6.1。保持现有 NSNet2、FD AEC、硬件参考、输入增益和扬声器音量参数。

## 长回复故障与证据

基线已复现问题。云端一段 24 kHz、16 bit、单声道回复含 2,697,600 个采样，
即 112.4 秒音频，却在约 53.91 秒内交付，峰值待播积压约 58.51 秒。
典型 `response.audio.delta` 为 15,360 字节，即 320 ms。
旧实现把它拆为 4,800 + 4,800 + 4,800 + 960 字节四个包，
100 包的解码入口限制只能容纳约 8～10 秒这种音频。

设备串口反复报告 `Decode queue is full, dropping incoming frame`，累计约 955 包。
基线实际 Speaking 状态持续约 64.88 秒，输出 trace 约 63.64 秒，随后回到 Listening，
而云端已交付 112.4 秒。内容被丢弃足以造成跳跃、听感像快放及提前结束。
这些证据没有证明 I2S 时钟改变；如果后续仍出现真实音调或速度变化，需要另测 DAC 输出。

对完全相同的云端事件、PCM 和发送时间进行本地 WebSocket 重放，修复版接收并向 codec
提交全部 2,697,600 个采样，解码入口丢包为 0。另一次真实云端长对话交付 69.36 秒，
1,664,640 个采样同样全部提交，入口丢包为 0。

## 实现

- PSRAM 配置保留正常云端 delta，单包上限 24,000 字节；普通 320 ms delta 直接转移 payload 所有权。
- Aliyun + PSRAM 下 PCM 解码入口同时限制 256 包和 3 MiB PCM；网络回调不等待扬声器。
  Opus 入口仍限制 100 包；无该 PSRAM 配置的协议包仍为 4,800 字节、入口 100 包。
- 与 DAC 采样率相同的 PCM 直接持有接收包，避免创建 Opus 解码器和整包复制。
  输出仍按最多 20 ms 分块，每块检查取消代次，沿用实际写入对应的 AEC 参考。
- 播放预缓冲按四个任务或 200 ms 样本判断，避免大包导致首音额外等待。
- 输入任务复用原生采样率和重采样缓冲；原始 PCM 调试点仍在重采样之前。
- AEC PCM trace 未开启时跳过仅用于诊断的左右声道拆分；保留 AFE 数据和参考时间线。
- 音频 Base64 普通格式走查表解码，其他格式回退 mbedTLS。输入长度、PCM 偶数字节检查保留。
  此快路径仅用于音频，不用于密码或密钥。
- `/api/test/stats` 增加队列长度、PCM 字节、播放样本、丢包数、接收/提交采样数，便于区分
  网络交付、排队和实际提交。32 bit 累计采样数按模差值统计；打断时接收大于提交属于预期。

录音测试队列保持原有时长限制；与解码队列共用物理容量以兼容 swap。
所有清空、出队、交换路径更新相应计数。

## CPU 对照方法和结果

按 IDF 本地官方文档 `docs/en/api-guides/performance/speed.rst` 的建议先测热点，再优化。
上述 112.4 秒音频按原事件时间重放，开启 Realtime、AEC、NSNet2 和持续麦克风上行。
关闭设备大流量 PCM trace；每秒左右读取任务运行计数，以 Speaking 起点后的前约 45 秒为对照窗口。
总忙碌率以双核全部算力为 100%，单核忙碌率各自以一个核为 100%。
这是同一录音的一次对照，不是多轮统计置信区间，也不含云端 TLS 和全量 trace 的开销。

| 版本 | 双核平均忙碌 | 核 0 | 核 1 | Feed 平均耗时 | 解码丢包 | 完整采样 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 基线，`-Os` | 63.00% | 46.86% | 79.15% | 22.05 ms | 基线串口有大量丢包 | 否 |
| 缓冲/拷贝修复，`-Os` | 63.91% | 48.96% | 78.87% | 21.99 ms | 0 | 是 |
| 缓冲/拷贝修复，`-O2` | 63.07% | 47.79% | 78.35% | 22.07 ms | 0 | 是 |
| 加音频 Base64 快路径，`-O2` | 53.59% | 32.11% | 75.07% | 21.79 ms | 0 | 是 |
| 最终版本，快路径 + `-Os` | 53.67% | 32.14% | 75.20% | 21.72 ms | 0 | 是 |

仅复用缓冲和减少拷贝没有测到稳定的平均 CPU 收益，其作用主要是减少分配和保护长播放。
Base64 快路径在相同 `-O2` 条件下使总忙碌率降低约 9.48 个百分点。
最终保留原有 `-Os`；单独改 `-O2` 的收益很小，增加约 288 KiB 固件和内部内存压力。
最终 `-Os` 版本相对基线降低约 9.34 个百分点。相对未加快路径的 `-Os` 修复版降低约
10.25 个百分点；网络接收任务 `tcp_receive` 的开销显著下降。最终回放窗口 Feed 超时和
Fetch 错误均为 0。完整回放仍观测到 2 个上行编码丢包，不能据此声称上行零丢包。

AFE 的 Feed 约 22 ms/32 ms 输入块，仍是核 1 的主要成本。继续大幅降低这个成本将涉及算法
或音质取舍，本次没有改变它。240 MHz 已启用；没有增加数据 cache 或挤占内部 RAM。

## 内存与边界

修复 `-Os` 对照中内部空闲内存最低观测约 69.1 KiB、最大连续块最低 34 KiB；
PSRAM 最低约 1.95 MiB。开机以来内部内存历史最低为 33,468 字节，
不能把测试期间的空闲量解释为所有瞬时场景的保证。峰值解码 PCM 为 2,753,280 字节、180 包。
基线 PSRAM 最低约 4.16 MiB，但这是边丢音频边释放形成的较低占用。

最终 `-Os` 实测：内部空闲最低观测 76,067 字节（74.28 KiB），最大连续块最低 40 KiB，
PSRAM 最低 2,152,100 字节（2.05 MiB），解码队列峰值 2,661,120 字节、174 包。
全部接收/提交 2,697,600 个采样，队列排空后回到 Listening。状态采样间隔约一秒，
Speaking 观察跨度约 111.49 秒并非精确 DAC 时长，完整性以该次采样计数和无取消为依据。

3 MiB 仅约束解码入口 PCM payload；还要加最多八个播放任务、解码/输出在途包、对象和其他模块。
在该格式下 3 MiB 约等于 65.536 秒，且包数上限也可能先触发。它覆盖本次峰值约 58.51 秒积压，
不能保证任意长、持续快于播放的服务器输出。超过上限仍明确计数丢包。
将来如需无限长回复，应设计上游流控、时长限制或流式存储，而不是无界增长。

## 验证与限制

- ESP32-S3 上临时启动自测：1,029 组不同长度的随机音频，经 mbedTLS 编码后用快路径解码逐字节比较；
  同时检查 padding、短缓冲、非法输入和哨兵边界，全部通过。自测代码已从最终源代码移除。
- 三组 10 秒硬件 AEC 测试：远端、近端、双讲均完成，trace gaps=0、削波=0、Feed 超时=0、Fetch 错误=0。
  远端单讲中段 mic/output 衰减约 40 dB；近端和双讲保留语音。该衰减不是通用 ERLE 测量。
- 真实云端 69.36 秒测试完整提交全部采样，未见额外误触发用户轮次。开启原始 PCM trace 时仍有上行
  编码丢包和 trace gaps，因此这份大流量诊断记录不能作为无间隙 AEC 录音验收。
- 主机完整测试曾运行 168 项：129 通过、33 跳过、6 环境错误。
  其中 5 项是 Windows 临时目录占用/清理失败，1 项缺主机 C++ 编译器。
  最后定向运行 7 项 C++ 测试全部因缺编译器跳过，不能称为通过；对应硬件和构建结果单独记录。
- Realtime 评估脚本的 12 项 Python 测试通过。
- 最终规范板型构建与烧录通过，应用大小约 `0x290150`，OTA 应用分区剩余 35%。
  串口确认 flash hash 校验和 Done；当前启动配置为 NSNet2、FD_LOW_COST/NLP_NORMAL 与硬件参考。
  临时解码启动自测不在最终固件内；触及的 C/C++ 文件通过 clang-format 检查。
- 播放积压时停止会话的回归通过：停止前解码队列 31 包、476,160 字节，播放队列八个任务；
  下一次采样已为 Idle、两个队列和 PCM 字节数均为 0，没有解码或上行编码丢包。
  停止前后提交计数差为 1,440 个采样（60 ms），包含 HTTP、状态采样和 DMA 时序，
  不能把它解释为精确声学停止延迟。
- **真实云端语音打断回归未通过。** 在实际开始播放 15 秒后，由电脑播放“你好，请回答八加五等于多少”，
  两次普通音量测试及一次将测试 WAV 的 RMS 提高约 7.2 dB 的测试均未收到第二个
  `input_audio_buffer.speech_started`，也没有对应转写/回答。第一轮连接在观察结束前关闭，
  后两轮连接持续到测试主动停止。第二轮已确认打断期间仍有连续上行、无编码/解码丢包，
  上行 PCM 的语音幅度明显高于仅远端播放时，但没有触发云端 VAD。
  因此尚不能确定是拾音强度、处理后的语音特征、云端检测还是其他环节；
  本次没有为让测试通过而改变设备增益、NS/AEC 或服务端 VAD 阈值，也没有基线 A/B 证明此现象的归属。
  “软件停止能清空缓存”与“声学打断识别通过”必须分别记录。
- 当前只实测此 S3 Wi-Fi 板；其他芯片、MQTT/UDP 运行、唤醒词声学回归和长期多轮压力仍需硬件覆盖。
  编译成功不代表这些路径已完成硬件验证。采样提交计数也不等于物理扬声器录音证明。

测试日志、固件备份和录音在本地 `tmp-audio-tests/cpu-opt-20261114/`，由 gitignore 排除。
新增 ES8311 本地资料 PDF 的精确忽略项；不删除现有文件。NVS、密钥和原代理配置在测试后恢复。

## 2026-11-15 上行连续性修复

复核设备 `a4:cb:8f:d7:6e:c0` 的会话 `bdadd17aacbf23d650a201f2`：原始输入约
66.25 秒，而上行 PCM 只有约 50.76 秒；输入时间戳跨度仍接近 67 秒，说明采集没有停止，
而实时上行链路在编码、排队或主任务发送阶段丢弃了约 15.5 秒的帧。

修复内容：

- 编码队列从 2 帧扩为 8 帧，发送队列从 2.4 秒扩为 7.2 秒；队列仍有界，满时保留最新实时帧。
- `OpusCodecTask` 优先处理麦克风上行编码，再处理下行解码，避免长回复解码挤占上行。
- 主任务每次最多排空 16 个上行包，发送队列可持续触发下一轮排空。
- `/api/test/stats` 增加发送队列深度、入队/出队、丢弃、产包和编码错误计数。

ESP32-S3 实测固件烧录成功。长回复 Realtime 会话收到 2,024 个 60 ms 上行包，
共 121.44 秒 PCM，代理会话跨度约 122 秒；会话建立后发送队列丢包计数不再增长，
与原来约 50 秒上行相比已恢复连续上传。测试期间 AFE feed/fetch 错误和超时均为 0。
