# Go Realtime 调试代理详细设计

状态：当前方案将 Go 服务定义为内网 WebSocket Debug Proxy。ESP32 可以通过 URL 选择直连阿里云，或连接 Go Proxy；Proxy 终止两端 WebSocket，复制鉴权 Header，按收到顺序原样转发应用层帧，并旁路记录完整交互。现有 TCP Collector、文件存储和网页工作台保留为兼容的设备诊断/离线分析能力，不再作为 Realtime 主链路。配套 [阿里云 Realtime 直连设计](aliyun-realtime-design.md)。

## 1. 目标

开发者需要回答四个独立的问题：

1. 麦克风经过 AEC、重采样和分帧后，设备准备发送的 PCM 样本是什么？
2. 阿里云 WebSocket 客户端实际尝试发送了哪些应用层消息，发送调用返回了什么？
3. 设备从阿里云实际收到哪些应用层消息、文本、音频片段、工具调用与错误？
4. 收到的音频经过解码、重采样后，进入本地播放队列的 PCM 是什么？

Go 服务在开发电脑运行时，既可以作为透明代理，也可以单独接收旧版固件的诊断流。Proxy 模式不保存长期 API Key：ESP32 在连接 Proxy 时按原有方式发送鉴权 Header，Go 只在内存中复制这些 Header，使用它们建立上游阿里云 WebSocket，连接结束后释放。Proxy 不向设备下发会话控制命令，不改变应用层消息内容或顺序。用户可在网页按会话查看双向原始帧、音频、信令时间线与转发耗时，并导出诊断包。

“实际发送”在本文特指**传给 WebSocket 库的应用层消息及该发送调用的结果**，不代表 TLS 字节、远端已收到或模型已处理。远端接受与处理须由对应云端事件证明。网页必须分别标注“准备发送”“发送调用成功”“云端事件确认”，避免混淆。

## 2. 代码与数据位置

计划新增仓库目录 `tools/realtime-debug/`，独立 Go module，不加入 ESP-IDF `main/CMakeLists.txt`：

```text
tools/realtime-debug/
  go.mod
  cmd/realtime-debug/main.go       启动参数、监听、退出
  internal/proxy/                 双 WebSocket 连接、Header 透传、顺序转发
  internal/trace/                 帧协议、校验、会话组装
  internal/store/                 顺序写入、索引、清理
  internal/web/                   HTTP API、实时推送、WAV 导出
    static/                      页面源码和静态资源（由此包内嵌）
  README.md                       运行、设备连接和数据解释
```

目录可随实现复杂度收缩；上述划分表达责任，不要求为每个概念单独建包。调试数据默认写到操作系统用户数据目录下的 `xiaozhi-realtime-debug`，并允许 `--data-dir` 指定。数据目录不得默认为仓库内路径；即使显式指定仓库内路径，也应有忽略规则，防止语音和原始消息被提交。

## 3. 端到端数据流

```text
ESP32                         开发电脑                         阿里云
┌───────────────┐        ┌─────────────────────┐        ┌───────────────┐
│ WebSocket 客户端 │        │ Go Debug Proxy      │        │ Realtime WS   │
│ URL 决定直连/代理 │───────►│ ESP32 侧 WS          │───────►│ 上游连接       │
│ 原有鉴权 Header  │        │ 上游 WS             │◄───────│ 原样应用帧     │
└───────────────┘        │ 双向 FIFO +旁路记录 │        └───────────────┘
                         │ 网页/会话/音频存储  │
                         └─────────────────────┘
```

Proxy 的两条转发路径各自只有一个严格 FIFO：ESP32 -> 阿里云、阿里云 -> ESP32。收到的 WebSocket 文本帧和二进制帧按原顺序转发，不按音频/信令分类，不让控制消息插队，不合并、拆分、重排或重写 JSON。Go 可以旁路解析 JSON 和音频字段用于统计，但解析结果不能参与调度。

ESP32 本地诊断 tap 仍尽量位于媒体转换或 WebSocket 收发的最后一个可信边界：上行 PCM 在云端格式转换后，TX 在交给 WebSocket 库前，RX 在收到完整应用层消息后，播放 PCM 在进入播放队列前。Proxy 模式下完整 WebSocket 和音频记录由 Go 完成，设备不再额外复制同一份大 payload 到旧 Collector；本地只保留 AEC、VAD、队列和播放状态等轻量诊断。

Proxy 始终记录原始 WebSocket 帧；音频信息作为旁路统计和原始数据保存，不改变转发内容。若下行云端返回的不是 PCM，服务保留原始编码数据，并记录 codec、采样率、声道和持续时间；只有确认格式后才额外生成 WAV。

## 4. 固件侧诊断契约（Proxy 模式下为可选旁路）

### 4.1 记录类型

| 类型 | 内容 | 记录时机 |
| --- | --- | --- |
| `session_open` / `session_close` | 本地 trace ID、模式、连接代次、断开原因 | 每次阿里云会话边界 |
| `pcm_uplink` | 转换后 PCM 字节和准确格式 | 放入云端音频事件前 |
| `ws_tx` | WebSocket 应用层消息原始字节、文本/二进制标记、消息 ID | 调用发送 API 前 |
| `ws_tx_result` | 对应消息 ID、API 返回值、耗时、已接受字节数（若可得） | 发送 API 返回后 |
| `ws_rx` | 收到的应用层消息原始字节、文本/二进制标记 | 业务解析前 |
| `pcm_playback` | 送往播放队列的 PCM 字节和格式 | 下行转换后 |
| `local_event` | 唤醒、Manual 松键、VAD、取消、队列排空、状态转换、重连 | 主任务确认相应动作时 |
| `trace_gap` | 被丢弃的调试记录数量、字节数、序号范围和原因 | 调试队列溢出/传输失败后 |

音频元数据至少包括采样率、声道数、每样本位数、字节序、样本格式（如有符号整数/浮点）、每帧样本数及 PCM 阶段。不得以 WAV 文件名推断这些值。非 PCM 原始消息保留其 WebSocket 文本/二进制类型，不做无依据的解码。

每条记录带 `boot_id`、`trace_session_id`、`connection_generation`、设备递增 `seq`、单调时钟 `mono_us` 和 `kind`。已知时追加云端会话 ID、回复 ID、事件类型和调用 ID；未知时保留空值，不能根据邻近事件臆造关联。`boot_id + seq` 在一次启动期间唯一；重连后 `trace_session_id` 可延续用户对话，但 `connection_generation` 必须更新。

### 4.2 性能边界

tap 只做有界复制与入队，不能做文件写入、JSON 美化、base64 解码、网络连接或等待调试服务。调试发送由独立低优先级任务处理，固定队列和固定最大占用；具体字节预算通过无 PSRAM 和有 PSRAM 代表板测量后确定，不能假定所有板都有 PSRAM。若复制失败，丢弃调试副本并累计缺口计数；正式阿里云收发和播放继续执行。大消息按片复制并标注消息 ID、分片序号、总长度；Go 端只有在分片完整时才展示为完整原始消息。

调试连接断开时停止排队旧数据，发布可用的 `trace_gap`/连接状态统计；重连后从新序号继续，不假装补齐。调试任务不得挤占 `AudioService` 的实时任务、扩大现有音频队列或改变丢包策略。每次启用时记录调试模式和固件版本，以便比较调试开关对语音延迟的影响。

### 4.3 数据真实性

`ws_tx` 是“尝试发送”；`ws_tx_result` 仅说明本地发送 API 返回状态。即使 API 成功，也可能随后断线、被服务端拒绝或未进入模型处理。网页按同一消息 ID 把两者并排展示，云端确认另列 `ws_rx` 事件。调试副本丢失、固件业务队列丢失、云端没有回复是三类不同问题，应有不同统计。

## 5. ESP32 到 Go Proxy 的连接

ESP32 保留现有阿里云配置，通过 WebSocket URL 选择直连或代理：

```text
wss://<aliyun-endpoint>/...       -> ESP32 直连阿里云
ws://<debug-host>:<port>/realtime -> ESP32 连接 Go Debug Proxy
```

直连时继续使用设备上的 API Key。Proxy 模式下，ESP32 仍按原有流程生成 WebSocket 握手 Header，将 `Authorization`、API Key、Workspace 等上游业务 Header 发给 Go；Go 不把 Key 写入文件或长期配置，只在内存中复制并用于建立阿里云上游连接。URL 判断为 Proxy 后，设备不得把 Key 放入 JSON、URL 或诊断日志之外的其他位置。

Go Proxy 终止 ESP32 一侧的 WebSocket，再建立一条到阿里云的新 WebSocket，因此不能复用原始 TCP/TLS 握手；但应用层文本帧、二进制帧和 Header 语义保持一致。Go 重新生成 `Connection`、`Upgrade`、`Sec-WebSocket-*` 等连接级 Header，仅复制上游需要的鉴权和业务 Header。任意一侧连接建立失败时，不开始转发业务帧，并向另一侧返回明确的连接错误。

现有设备管理页继续保存阿里云 URL、地域、Workspace 和 API Key；调试配置新增 Proxy URL 或直接允许替换 WebSocket URL。Proxy 模式不再依赖设备独立 TCP Trace 连接来获得完整协议记录。旧版 `dbg_enable`、`dbg_addr`、`dbg_level` 仍可用于 AEC/本地事件诊断，但不应在 Realtime 主链路中复制完整 WebSocket 和 PCM payload。

Proxy 只在受控开发局域网运行。它可以不要求额外的设备配对令牌，但必须禁止公网暴露；因为 API Key 会在握手期间经过 Go，日志和网页必须对所有鉴权 Header 脱敏。若未来需要跨网段或长期运行，再增加独立的设备认证，不把 API Key 当作设备身份凭证。

旧 TCP Collector 使用长度前缀的版本化二进制帧：

```text
uint32_be frame_length     // 不含本字段，服务端设严格上限
uint16_be protocol_version
uint16_be frame_kind
uint32_be metadata_length
metadata JSON UTF-8        // 标识、序号、格式、分片和状态
payload bytes              // 原始 WS 消息或 PCM，允许为空
```

接收端先验证总长度、版本、类型、元数据长度和必填字段，再按需分配。单帧最大值为配置项；默认值必须小于固件可承受的缓冲预算，过大的 WebSocket 消息由固件分片发送。接收顺序由 TCP 保证，但完整性以 `seq` 和分片信息检查。设备连接后第一帧发送 `hello`，包含设备标识（脱敏）、固件版本和可用 tap；协议版本不匹配则明确拒绝。`seq` 在 JSON 与网页 API 中作为字符串传输，避免浏览器整数精度损失。

旧 TCP 采集服务只接受一条设备诊断连接，不向设备返回“修改模式”“调用工具”或“发送音频”等命令。它用于旧版固件、AEC 专项测试和离线样例，不参与 Proxy 的实时转发。服务停止、磁盘满或 TCP 连接失败时，设备记录诊断状态但不影响云端连接。服务端对每秒字节数和总磁盘量限流，不能让设备输入耗尽电脑内存或磁盘。

## 6. Go 服务内部设计

### 6.1 并发模型

每个 Proxy 会话包含 ESP32 侧 WebSocket、阿里云侧 WebSocket，以及两个单向转发循环。每个方向只有一个 FIFO 和一个写入协程：读取、入队、写出严格保持顺序。控制消息不享有额外优先级，音频也不被单独丢弃；任何过载都应表现为真实的 WebSocket/TCP 反压，而不是由 Debug 代码重新调度。

转发路径只负责帧复制和写出。JSON、音频格式和事件 ID 的解析在旁路 trace pipeline 中完成，不能阻塞读协程或写协程。每个帧记录 `recv_at`、`forward_start_at`、`forward_done_at`、方向、帧类型、长度和顺序号；解析失败仍保存原始帧。鉴权 Header 只存在于会话内存，记录器收到的元数据必须已经脱敏。

记录器使用独立异步写入队列。队列满或磁盘变慢时，Proxy 继续转发，不丢弃实际协议帧；只丢弃调试副本并写入 `trace_gap`，包含缺失帧序号和原因。网页查询只读已提交的索引，实时更新用 SSE 推送摘要，不经 SSE 推送大块 PCM 或 base64。Go 服务收到退出信号时先停止新连接，再关闭两侧 WebSocket、冲刷可用记录并标记未完成会话。

旧 TCP Collector 继续使用原有单读取协程和顺序写入器，不与 Proxy 的 WebSocket 转发路径共享队列。

### 6.2 落盘格式

每个会话一个目录，避免每个音频帧创建小文件：

```text
<data-dir>/<date>/<boot-id>/<trace-session-id>/
  manifest.json       设备/会话/格式段/起止时间/完整性/统计
  events.jsonl        每条记录的索引、时间、类型、关联 ID、偏移与长度
  payloads.dat        按到达顺序追加的原始 WS 负载和其他二进制负载
  pcm-uplink.dat      上行 PCM 顺序数据
  pcm-playback.dat    播放 PCM 顺序数据
```

索引记录引用各数据文件的偏移和长度。PCM 格式改变时在 `manifest` 中开启新格式段，不把不同采样率或声道直接拼接成一段 WAV。网页请求 WAV 时按格式段流式生成头和音频，下载也走同一逻辑。写入顺序先数据后索引；重启恢复时扫描并截去不完整尾记录，`manifest` 用临时文件替换以避免半写。大原始消息和音频不常驻 Go 内存。导出包包含清单、索引、原始负载和可用的 WAV，并保留 `trace_gap`，便于离线复盘。

初版设置可配置的会话大小、总大小和保留时间上限。超过会话上限时停止该会话的录制并明确标为截断；总空间不足时按保留策略删除最旧的**已结束**会话，不删除正在查看或写入的会话。删除动作在网页中需明确显示将移除的录音和原始消息。

### 6.3 HTTP API

| API | 用途 |
| --- | --- |
| `GET /api/sessions` | 分页获取会话摘要、时间、模式、完整性与错误数 |
| `GET /api/sessions/{id}` | 获取清单、轨道和统计 |
| `GET /api/sessions/{id}/events` | 按时间/类型/方向/回复 ID 分页查询事件摘要 |
| `GET /api/sessions/{id}/events/{seq}` | 单条事件详细元数据与有界原始负载 |
| `GET /api/sessions/{id}/audio/{track}.wav` | 按 PCM 格式段流式试听或下载 |
| `GET /api/live` | SSE 推送新会话、事件摘要、连接和丢弃统计 |
| `GET /api/sessions/{id}/export` | 流式导出完整诊断包 |

API 返回明确的 `capture_complete`、`trace_gap_count`、`send_result` 等字段。原始消息可能包含用户语音和文本，详情 API 做响应大小限制，超大负载需通过导出包取得。路径参数不直接拼成文件路径；会话目录由受控索引查找，防止路径穿越。

## 7. 网页工作台

网页默认监听 `127.0.0.1`，与设备采集端口分开。首屏直接进入调试工作台，不做介绍页：

- 左栏：设备与会话列表，显示开始时间、模式、在线/结束/截断状态和错误标记。
- 中栏：统一时间线。上下行、PCM、本地状态、工具调用、错误用方向与图标区分；可按事件类型、回复 ID、关键词筛选，放大查看相邻事件耗时。
- 右栏：选中事件的精确时间、序号、关联 ID、发送调用结果、原始 JSON/二进制摘要和字节数。原始内容可复制或下载，默认不展开大块 base64。
- 音频区：上行与播放 PCM 双轨时间轴，支持播放、暂停、定位、循环选段和按段下载 WAV。波形由服务端降采样摘要绘制，浏览器不一次加载整段录音。
- 状态栏：设备连接、固件采集级别、丢失记录、队列溢出、磁盘占用和服务端错误。

时间线以设备 `mono_us` 为主，Go 接收墙钟作为旁注。跨设备或重启不能直接比较单调时钟；网页展示时用 `boot_id` 区分。网络传输延迟通过“设备时间/Go 接收时间”分析前须先校准时钟，第一版只显示相对时序，不宣称精确单向网络延迟。

典型排查路径：选中一次用户发言 -> 听上行 PCM -> 看对应 TX 消息及发送结果 -> 看服务端识别与回复事件 -> 听播放 PCM -> 看本地播放排空和状态变化。页面应保持这些事件的关联，不要求开发者手工对照多份日志。

## 8. 隐私与访问控制

Proxy 会在内存中接触 ESP32 发来的鉴权 Header，但不保存长期 API Key，不写入配置、trace、网页或导出包。日志只记录 Header 名称和脱敏后的存在状态；原始 WebSocket 应用 payload 中若意外出现凭证字段，显示层也必须遮蔽。原始音频、对话文本和应用消息仍然敏感，导出前给出明确提示。

Proxy 和旧采集端都只用于受控开发网络。Proxy 监听地址不得映射到公网；网页默认绑定 `127.0.0.1`。调试默认关闭，正式固件不提供远程启用完整抓包的入口。旧采集流使用无认证明文 TCP，Proxy 的 WebSocket 也只在内网使用；未来跨网段时应增加设备级认证，而不是把 API Key 直接当作配对机制。

Go 查看网页可一键停止 Go 端接收与落盘；设备侧采集开关在设备管理页关闭，Go 网页不通过调试协议控制设备。服务端提供删除会话及自动清理策略。默认不上传云端、不发送遥测、不自动分享采集包。固件出厂或正式发布构建不得包含可远程启用的抓包入口。

## 9. 实施与验收顺序

Go debug 服务不编写 UT；以下步骤通过运行 Proxy、导入样例和连接实体设备进行人工验证。

1. 增加 Proxy 监听入口和 URL/端口配置，验证 ESP32 握手 Header 能建立上游阿里云连接，且任何日志都不泄露 API Key。
2. 实现双向单 FIFO 原样转发，使用文本帧、二进制帧、连续音频帧和大 payload 验证顺序、边界和关闭传播。
3. 增加旁路帧记录、JSON 事件摘要、上下行原始音频和转发时间戳；记录器降速或队列满时验证只出现 `trace_gap`，不改变协议帧。
4. 修改 ESP32，使 URL 能在直连和 Proxy 间切换；Proxy 模式关闭完整设备侧 WebSocket/PCM Trace，只保留 AEC、VAD、队列和播放状态诊断。
5. 在真机验证 Manual、Auto、Realtime、插话、`response.cancel`、迟到事件、断线和重连；对照 Proxy 记录确认控制信令和音频帧没有重排。

人工验收覆盖：直连与代理结果对比、鉴权 Header 脱敏、无效 Key、上游拒绝、ESP32 断电、阿里云断线、Proxy 重启、慢接收、磁盘满、大帧、纯文本回复、无音频回复、取消后的迟到包和完整上下行音频还原。验收标准是 Proxy 故障不会改变直连模式，Proxy 模式不分类调度、不主动丢协议帧，所有记录缺口都可见。
